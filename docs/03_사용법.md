## 0. 5분 개념 정리 — 무엇이 무엇을 하는가

이 스택에서 각 조각의 역할이 겹치지 않는다. 이것만 구분되면 나머지는 전부 조립이다.

| 조각 | 역할 | 이 프로젝트에서 |
|---|---|---|
| **ROS 2 (Jazzy)** | 프로세스 사이 통신(토픽·액션·파라미터·TF)과 빌드 시스템 | 모든 노드가 여기 위에서 돈다 |
| **URDF / xacro** | 로봇의 **기구학·형상** 정의(링크·관절·한계·메시). xacro는 URDF를 만드는 매크로 언어 | `so101.urdf.xacro` → 백엔드 3종을 인자로 고른다 |
| **SRDF** | 로봇의 **의미** 정의(Planning Group, 저장 자세, 자기충돌 예외) | 업스트림 것을 재사용 (`arm`, `gripper`) |
| **MoveIt 2** | 목표 → **경로 계획**(충돌 회피·IK·시간 파라미터화), 계획을 컨트롤러로 넘김 | `/move_action` 서버(`move_group` 노드) |
| **ros2_control** | 컨트롤러와 장치를 잇는 **실행 계층** | `controller_manager` + JTC 2개 + state broadcaster |
| **JTC** (joint_trajectory_controller) | 시간 궤적을 **보간·전송**하고 tolerance를 감시, 액션 결과 반환 | `arm_controller`, `gripper_controller` |
| **하드웨어 인터페이스** | 컨트롤러의 명령을 **실제 장치/시뮬레이터**에 쓰고 상태를 읽음 | `mock` / `mujoco` / `real` 3종 |
| **MuJoCo** | **물리 엔진**(중력·접촉·관절 동역학). GUI가 아니라 라이브러리 | `mujoco_ros2_control`을 통해 위 인터페이스로 붙는다 |
| **MJCF** | MuJoCo의 **모델 포맷**(URDF와 별개 파일) | `mjcf/scene.xml` (MuJoCo Menagerie 모델) |
| **RViz2** | **시각화**. 물리를 계산하지 않는다. 상태·계획 경로·목표 마커를 보여줌 | MoveIt MotionPlanning 패널로 계획 시연 |
| **colcon workspace** | 패키지를 빌드해 `ros2 run/launch`로 부를 수 있게 만드는 작업 폴더 | `~/so101_ws` |

흐름 한 줄:

```
목표(그룹+관절값) → MoveIt 2 계획 → JTC 실행 → 하드웨어 인터페이스 → mock | MuJoCo | 실물
                                                        ↓ 측정 상태
                                        /joint_states · TF → MoveIt · RViz
```

## 1. 준비

### 어느 배포판에서 하는가

```powershell
wsl -d Ubuntu          # Ubuntu 24.04 = 작업 배포판 (ROS 2 Jazzy)
```

`Ubuntu-22.04`는 ROS 2 **Humble**이 들어 있는 별개 환경이다. 삭제하지 않고 그대로 두되,
**한 셸에서 Humble과 Jazzy를 같이 source하지 않는다.**

### 모든 새 터미널에서 하는 한 줄

```bash
source scripts/env.sh
```

이 한 줄이 세 가지를 한다: ① ROS 2 Jazzy(`ros2` 명령) ② 우리 워크스페이스(`so101_project`)
③ **WSL 통신 우회**(`lib_dds.sh`, 7절 참고). ③이 빠지면 "노드는 떠 있는데 `ros2 topic list`가
비어 있다"가 된다.

**`ros2: command not found`나 `Package 'so101_project' not found`는 거의 항상 이 줄을 안 한 것이다.**
`~/.bashrc` 맨 아래에 넣어 두면 새 터미널마다 자동으로 준비된다:

```bash
echo 'source scripts/env.sh' >> ~/.bashrc
```

번호 붙은 스크립트(`04`·`05`·`06`·`07`)는 안에서 알아서 source 하므로 준비 없이 그냥 실행해도 된다.
우리 노드도 래퍼로 실행하면 준비가 필요 없다:

```bash
./scripts/08_run.sh leader_follow.py --source demo        # = ros2 run so101_project leader_follow.py ...
./scripts/08_run.sh ros2 control list_controllers         # ros2 명령도 통과시킨다
```

> `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`, `ROS_LOCALHOST_ONLY=1`,
> `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`는 **이 랩탑에서 쓰지 않는다.**
> 뒤의 두 개는 127.0.0.1을 강제하는데, 이 WSL은 그 경로가 죽어 있어서 통신이 아예 막힌다
> (7절 문제 해결 표와 `04_시나리오_실행법.md` 부록).

### 폴더 두 곳의 역할

| 위치 | 무엇 | 편집 |
|---|---|---|
| `<저장소 루트>` (Windows 쪽에 두면 편집이 쉽다) | **소스**(우리 패키지·스크립트·문서·MJCF) | Windows 편집기로 자유롭게 |
| `~/so101_ws` (WSL 홈) | **빌드 워크스페이스**. `src/so101_project`가 위 폴더로 심볼릭 링크 | 직접 편집하지 않음 |

```
~/so101_ws/
├─ src/       빌드 대상: so101_project(링크), so101_description(링크), so101_project_moveit_config(복사본)
├─ build/     중간 산출물          ├─ install/  빌드 결과 (setup.bash 여기 있음)
├─ log/       빌드·실행 로그        ├─ vendor/   업스트림 clone 원본 (COLCON_IGNORE로 빌드 제외)
└─ artifacts/ 전개한 URDF·버전 기록
```

`--symlink-install`로 빌드하므로 **YAML·launch·xacro 수정은 다시 빌드하지 않아도 반영**된다.
`package.xml`·`CMakeLists.txt`를 바꿨거나 파일을 새로 추가했을 때만 다시 빌드한다.

## 2. 스크립트 사용법

순서대로 한 번씩 실행하면 시뮬레이터에서 팔이 움직이는 상태까지 간다.
`00`~`03`은 준비·점검이고, **실제로 로봇이 도는 것은 `06_bringup.sh`부터**다. `04`·`05`는 그 위에서 쓰는 도구이고, `07`은 통신이 막혔을 때 쓰는 진단·복구 도구다.

### `00_install_jazzy.sh` — 설치 (한 번, sudo)

`--gui`를 붙이면 **화면·GUI 도구만** 설치/확인한다(짧고, 여러 번 실행해도 안전하다).
`05_gui.sh`의 `leader`·`sliders`·`rqt`·`foxglove`가 안 될 때 이것을 먼저 실행한다.

```bash
./scripts/00_install_jazzy.sh --gui
```

```bash
./scripts/00_install_jazzy.sh
```

- **하는 일:** codename(noble) 확인 → 기본 빌드 도구·`libserial-dev` → ROS apt 저장소 → 후보 버전 확인 →
  `ros-jazzy-desktop` + MoveIt 2 + ros2_control + `mujoco_ros2_control` + GUI 도구 설치 → `rosdep` 초기화.
- **오래 걸린다:** 400개 이상 패키지, 수 GB. 10~40분은 정상이다.
- **성공 신호:** 마지막에 환경 변수 안내가 출력된다. 확인은
  `ros2 pkg prefix mujoco_ros2_control`, `ros2 pkg prefix moveit_ros_move_group`.
- **여기서 먼저 확인할 것(권장):** SO-101과 무관한 공식 데모로 MuJoCo·GUI가 되는지 본다.

```bash
ros2 launch mujoco_ros2_control_demos 01_basic_robot.launch.py     # MuJoCo 창이 떠야 한다
ros2 control list_controllers                                       # 다른 터미널
```

### `01_setup_workspace.sh` — 워크스페이스 구성·빌드

```bash
./scripts/01_setup_workspace.sh              # 기본 (sudo 불필요)
./scripts/01_setup_workspace.sh --with-real  # + libserial-dev 설치 후 실물 드라이버까지 빌드 (sudo 물어봄)
./scripts/01_setup_workspace.sh --rosdep     # + rosdep 의존성 설치 (sudo 물어봄)
```

- **하는 일:** `~/so101_ws` 생성 → 업스트림 저장소 clone(서브모듈 포함) → `vendor/COLCON_IGNORE` 생성 →
  `src`에 필요한 패키지만 링크 → **업스트림 MoveIt config 복사 후 패치**(패키지 이름,
  `manipulator`→`arm`, 컨트롤러 이름·그리퍼 타입) → `colcon build` → 버전·커밋 기록.
- **빌드 대상은 4개뿐이다:** `so101_description`, `so101_project`, `so101_project_moveit_config`,
  그리고 `libserial`이 있을 때만 `feetech_ros2_driver`.
  업스트림의 나머지(텔레옵·기록·추론 등)는 이 프로젝트에서 쓰지 않으므로 빌드하지 않는다.
- **실물 드라이버를 빌드하려면** `libserial-dev`가 필요하다. `00`을 처음부터 실행했다면 이미 깔려 있고,
  없으면 `--with-real`이 설치까지 해준다. 시뮬레이션(mock/mujoco)에는 없어도 아무 문제 없다.
- **성공 신호:** `Summary: 3 packages finished`(또는 4).
- **재실행해도 안전하다.** 이미 있는 clone·패치는 건드리지 않는다.
  MoveIt config를 처음부터 다시 만들고 싶으면 `rm -rf ~/so101_ws/src/so101_project_moveit_config` 후 재실행.

### `02_export_urdf.sh` — 모델 전개·검증

```bash
./scripts/02_export_urdf.sh
```

- **하는 일:** `so101.urdf.xacro`를 `hardware_type` 3가지로 전개해 `~/so101_ws/artifacts/*.urdf`로 저장,
  `check_urdf`로 트리 검증, 관절·한계·축·ros2_control 인터페이스 표 출력.
- **성공 신호:** robot name이 `so101_arm`이고 움직이는 관절 6개가 아래 값으로 나온다.

```
shoulder_pan  -1.91986 ~ 1.91986      wrist_flex  -1.65806 ~ 1.65806
shoulder_lift -1.74533 ~ 1.74533      wrist_roll  -2.74385 ~ 2.84121
elbow_flex    -1.69    ~ 1.69         gripper     -0.174533 ~ 1.74533
```

- 왜 이 단계가 필요한지는 **3절**에서 설명한다.

### `03_make_mjcf.sh` — MuJoCo 물리 모델 점검

```bash
./scripts/03_make_mjcf.sh              # 기본: 이미 들어있는 모델 점검
./scripts/03_make_mjcf.sh --convert    # 대체: 실험적 URDF→MJCF 변환기 실행
```

- **하는 일(기본):** `src/so101_project/mjcf/`의 모델이 온전한지, **관절 이름·범위·actuator ctrlrange가
  URDF와 맞는지** 표로 보여준다. 모델은 이미 프로젝트에 포함되어 있으므로 새로 만들 필요가 없다.
- **성공 신호:** 6개 관절이 모두 출력되고 범위가 위 URDF 값과 일치.
- 왜 MJCF가 따로 있는지는 **4절**.

### `06_bringup.sh` — **여기서 처음으로 로봇/시뮬레이터가 돈다**

`bringup`은 ROS 용어로 "로봇을 실행 상태로 올리는 launch"다. 노드·컨트롤러·MoveIt·RViz를 한꺼번에 띄우고
**그 터미널을 계속 점유한 채 돌아간다.** 종료는 `Ctrl+C`. 그래서 점검·제어는 항상 **다른 터미널**에서 한다.

터미널 1 (계속 점유):

```bash
./scripts/06_bringup.sh mock      # mock | mujoco | real
```

- 스크립트 안에서 `source`까지 하므로 `ros2: command not found`가 나지 않는다.
- 추가 인자는 그대로 전달된다: `./scripts/06_bringup.sh mujoco use_rviz:=false`
- 같은 일을 직접 하려면: `ros2 launch so101_project bringup.launch.py hardware_type:=mock`

### `04_smoke_test.sh` — 배선 점검

**전제: 다른 터미널에서 bringup이 돌고 있어야 한다.** 아니면 스크립트가 먼저 그 사실을 알려주고 멈춘다.

터미널 2:

```bash
./scripts/04_smoke_test.sh
```

- **하는 일:** 노드 목록, **컨트롤러 3개 active**, 하드웨어 인터페이스, `follow_joint_trajectory`·`/move_action`
  액션 존재, `/joint_states` 발행자 수(1개여야 한다), `/clock`(mujoco에서만), 그리고
  plan-only 요청 2건 + **잘못된 요청이 거부되는지**까지 확인한다.
- **성공 신호:** `arm_controller`, `gripper_controller`, `joint_state_broadcaster`가 모두 `active`이고
  plan-only가 `SUCCESS`, 그룹 밖 관절 요청은 거부(exit 2).

### `07_doctor.sh` — 통신이 막혔을 때 진단·복구

```bash
./scripts/07_doctor.sh          # 진단만 (아무것도 건드리지 않는다)
./scripts/07_doctor.sh --fix    # 복구 (ROS 프로세스 종료 + 고아 SHM 정리 + 데몬 정지 후 재시험)
```

- **하는 일:** 환경변수·시계·실행 중 ROS 프로세스·**127.0.0.1 통신 가능 여부**·`/dev/shm`의
  고아 Fast DDS 세그먼트를 점검하고,
  **서로 다른 프로세스 사이에 메시지가 실제로 오가는지 왕복 시험**을 한다. 실패하면 정리 →
  UDP 전용 → CycloneDDS 순서로 시도하며 어느 설정에서 되는지 알려준다.
- **언제:** bringup 로그에 `Waiting for data on 'robot_description' topic`이 계속 반복될 때,
  spawner가 서비스 접속에 실패할 때, 다른 터미널에서 `ros2 node list`가 비어 있을 때.

### `08_run.sh` — 우리 노드를 환경 준비까지 알아서 실행

```bash
./scripts/08_run.sh                                   # 인자 없이 실행하면 노드 목록을 보여준다
./scripts/08_run.sh leader_follow.py --source demo
./scripts/08_run.sh joint_command.py --deg shoulder_pan=30 --time 2
./scripts/08_run.sh group_goal_client.py --group arm --named rest --execute
./scripts/08_run.sh ros2 topic echo /joint_states --once
```

`.py`는 생략해도 된다. 첫 인자가 `ros2`면 그 명령을 그대로 실행한다.

### `05_gui.sh` — 화면 보며 제어 (촬영용)

```bash
./scripts/05_gui.sh viewer      # ROS 없이 MuJoCo 모델만 열기 (가장 빠름)
./scripts/05_gui.sh leader      # "가상 leader" 슬라이더 → /leader/joint_states (블로그 9편)
./scripts/05_gui.sh sliders     # 관절 슬라이더 → JTC → 팔이 움직임
./scripts/05_gui.sh rqt         # 컨트롤러 상태 + 노드 그래프
./scripts/05_gui.sh foxglove    # 브라우저: app.foxglove.dev → ws://localhost:8765
```

`viewer`는 `ros-jazzy-mujoco-vendor`가 같이 설치하는 **MuJoCo 공식 `simulate` 앱**
(`/opt/ros/jazzy/opt/mujoco_vendor/bin/simulate`)을 쓴다. pip 설치가 필요 없고, MuJoCo가 배포하는
그 프로그램 그대로다. 없을 때만 pip venv로 대체한다.

`leader`는 `joint_state_publisher_gui`를 `/leader/joint_states`로 리맵해 띄운다. 이 창은 로봇을
직접 움직이지 않고, `leader_follow.py --source topic`이 그 값을 컨트롤러로 옮긴다(미션 가이드 2-3절).

`sliders`는 창이 열린 뒤 **① controller manager를 `/controller_manager`로 선택 → ② controller를
`arm_controller`로 선택 → ③ 왼쪽 전원 아이콘을 눌러 활성화**해야 슬라이더가 살아난다.
`sliders`·`rqt`·`foxglove`는 apt 패키지가 따로 필요하다(없으면 스크립트가 설치 명령을 알려준다).

**두 슬라이더 창(`leader`와 `sliders`)을 동시에 쓰지 않는다.** 같은 컨트롤러에 두 곳에서
명령하면 서로를 덮어쓴다.

## 3. `02`가 왜 필요한가 — xacro/URDF 전개의 정석

**xacro는 파일로 만들어 두는 게 원칙이 아니다.** 정상 동작은 launch가 실행 시점에
`xacro`를 돌려 결과를 메모리(`robot_description` 파라미터/토픽)로 넘기는 것이다. 우리 `bringup.launch.py`도
그렇게 한다. 그래서 `02`가 만드는 `.urdf` 파일은 **런타임 입력이 아니다.**

그럼에도 파일로 뽑는 것이 ROS에서 표준 절차인 이유는 세 가지다.

| 목적 | 설명 | 정석 도구 |
|---|---|---|
| **검증** | 매크로·인자·경로 오류를 로봇을 띄우기 전에 잡는다. 실패하면 launch 안에서 "왜 안 뜨는지" 찾기 훨씬 어렵다 | `xacro model.xacro > out.urdf` → `check_urdf out.urdf` (`urdf_to_graphviz`로 트리 그림도 가능) |
| **도구 입력** | MoveIt Setup Assistant, URDF→MJCF 변환기, 시각화 도구는 **파일**을 요구한다 | 뽑아 둔 `.urdf` |
| **실측값 확인** | 관절 한계·말단 프레임·질량을 눈으로 확인해 설정 파일(`controllers.yaml`, `joint_mapping.yaml`)과 대조 | 02가 출력하는 표 |

우리가 **3가지 백엔드를 모두 뽑는** 이유: `hardware_type`에 따라 `<ros2_control>` 블록만 달라져야 하고
기구학은 절대 달라져서는 안 된다. 3개를 뽑아 비교하면 그 전제가 깨졌는지 즉시 보인다.

> 주의: 뽑아 둔 URDF를 "진실"로 삼아 계속 쓰지 않는다. 그 파일에는 특정 `hardware_type`이 박혀 있다.
> 항상 xacro가 원본이고, 실행은 launch가 그때그때 전개한다.

## 4. `03`과 MJCF가 왜 필요한가 — URDF와 MJCF의 관계

MuJoCo는 URDF도 읽을 수 있다. 하지만 URDF에는 **actuator(구동기), 접촉·솔버 파라미터, 초기 자세
keyframe, 시뮬레이션용 충돌 형상**이 없다. 그것들이 MJCF에만 있는 개념이라서, 실무에서는

```
URDF  = ROS·MoveIt 의 기준 모델 (기구학·한계·TF·계획)
MJCF  = MuJoCo 의 물리 모델      (actuator·접촉·솔버·keyframe)
```

**두 파일이 공존하는 것이 정상**이고, 관리 방법은 "한쪽에서 자동 생성"이 아니라 **관절 이름과 범위를
같게 유지하고 주기적으로 대조**하는 것이다. `03`이 하는 일이 정확히 그 대조다.

MJCF를 얻는 방법은 두 가지고, 이 프로젝트는 앞의 것을 골랐다.

| 방법 | 실제 |
|---|---|
| **큐레이션된 공개 모델** (선택) | MuJoCo Menagerie의 `robotstudio_so101`. DeepMind가 관리하는 공식 모델 모음이고, The Robot Studio 공식 MJCF에서 파생. position actuator 6개(kp 998.22, kv 2.731, forcerange ±2.94), 충돌 형상, 씬까지 완비 |
| URDF→MJCF 변환기 | `mujoco_ros2_control`이 제공하지만 공식 문서가 "hacky and _highly_ experimental"이라고 명시. actuator·ctrlrange·질량·keyframe을 손으로 채워야 한다 |

대조 결과 **관절 이름 6개와 범위가 우리 URDF와 일치**했고, 어긋난 곳은 `wrist_roll` 상한 한 곳
(2.7438473 vs 2.84121)이라 URDF에 맞춰 고쳤다. 여기에 SRDF `rest`와 같은 keyframe을 추가했다.

**어긋나면 나타나는 증상**을 알아두면 진단이 빠르다.

| 어긋난 것 | 증상 |
|---|---|
| 관절 이름 | 컨트롤러가 인터페이스를 못 찾아 로드 실패(`list_hardware_interfaces`가 비어 있음) |
| 관절 범위(MJCF가 좁음) | MoveIt은 성공했다는데 실측값이 목표에 못 미친다(시뮬레이터가 클램프) |
| 단위(도/라디안) | 조금만 움직여야 하는데 팔이 확 돌아간다 |
| 질량·kp | 팔이 처지거나 진동·폭주 |

## 5. MuJoCo 화면 개념 — 어떤 창이 "공식"인가

**MuJoCo 자체는 GUI가 아니라 물리 엔진 라이브러리다**(DeepMind). 그래서 "MuJoCo 화면"이라고 부르는 것은
엔진 위에 올라간 **뷰어 프로그램**이다. 공식 뷰어는 두 가지이고, 우리가 쓰는 창은 둘 다 공식이다.

| 창 | 정체 | 누가 로봇을 움직이나 | 언제 쓰나 |
|---|---|---|---|
| `05_gui.sh viewer` | **공식 Python 뷰어** (`mujoco` 파이썬 패키지의 `mujoco.viewer`, DeepMind 제공) | 아무도. 물리만 돌고 마우스로 관절을 끌어볼 수 있다 | 모델만 빨리 확인·촬영. ROS·빌드 불필요 |
| `bringup.launch.py hardware_type:=mujoco`로 열리는 창 | **공식 MuJoCo Simulate 앱을 ROS가 감싼 것.** `mujoco_ros2_control` 패키지 설명이 그대로 "ros2_control wrapper for the MuJoCo Simulate application" | **ROS 컨트롤러**(JTC ← MoveIt) | 실제 제어 검증·시연 |
| RViz2 | ROS 표준 시각화 도구 | 계획을 만들어 보낼 수 있음(MotionPlanning 패널) | 계획 경로·목표·TF·충돌 확인 |

정리하면:

- **물리 시뮬레이션 = MuJoCo 창.** 중력에 팔이 처지고 물체와 부딪히는 것은 여기서만 보인다.
- **계획·상태 시각화 = RViz.** 물리를 계산하지 않는다. MuJoCo가 없어도(mock) 뜬다.
- 둘은 같은 `/joint_states`를 보므로 **동시에 띄워 나란히 놓는 것이 정상 사용법**이다.
- **웹 시뮬레이터는 이 스택에 없다.** `05_gui.sh foxglove`는 ROS 데이터(토픽·TF·로봇 모델)를 브라우저에서
  보는 도구이고, MuJoCo의 물리 렌더링 화면 자체를 웹으로 옮기는 것은 공식 경로가 아니다.
- MuJoCo 창 없이 돌리려면 `mujoco_headless:=true`(원격·CI·성능 측정용).

ros2 run so101_project group_goal_client.py --group arm --named rest              # 계획만

## 7. 문제 해결

| 증상 | 원인·해결 |
|---|---|
| `AMENT_TRACE_SETUP_FILES: unbound variable` | 스크립트의 `set -u`와 ROS `setup.bash` 충돌. **수정 완료** — 스크립트를 다시 받아 실행 |
| `colcon`이 `so101_teleop`, `so101_inference` 등을 빌드하다 실패 | `vendor/`가 워크스페이스 안에 있어 colcon이 전부 훑은 것. **수정 완료**(`vendor/COLCON_IGNORE` + `--packages-select`). 이미 만든 워크스페이스라면 `touch ~/so101_ws/vendor/COLCON_IGNORE` 후 재실행 |
| `libserial` 없다며 `feetech_ros2_driver` 실패 | 실물 드라이버 전용 의존성. 시뮬레이션에는 필요 없다. 실물을 쓸 때 `./scripts/01_setup_workspace.sh --with-real`(설치+빌드 한 번에) 또는 `sudo apt install -y libserial-dev` 후 `01` 재실행 |
| `Package 'so101_project' not found` | 터미널에서 `source ~/so101_ws/install/setup.bash` 안 함 |
| 문서의 명령을 한 터미널에 통째로 붙여넣어 엉킴 | bringup은 터미널을 점유한다. **터미널 1/터미널 2 블록을 각각 따로** 붙여넣는다 |
| `ros2 control list_controllers`가 멈추거나 `TimeoutError: [Errno 110]` traceback | ros2cli 데몬이 응답하지 않는 상태. `ros2 daemon stop` 후 조회는 `--no-daemon`으로. 복구 절차는 `04_시나리오_실행법.md` 부록 |
| 로그에는 컨트롤러가 활성화됐는데 다른 터미널에서 아무것도 안 보임 | WSL의 프로세스 간 DDS/시계 문제. **`./scripts/07_doctor.sh --fix`** 를 먼저 실행 |
| bringup이 `Waiting for data on 'robot_description' topic`을 계속 반복 | **정상이 아니다.** 컨트롤러가 하나도 안 올라온 상태. `./scripts/07_doctor.sh`로 원인을 본다. 이 랩탑에서 측정으로 확정된 원인은 **WSL `networkingMode=mirrored`로 127.0.0.1 통신이 죽은 것**이고, `lib_dds.sh`가 자동 우회한다. 근본 해결은 `.wslconfig`에서 `networkingMode=mirrored` 삭제 + `wsl --shutdown` (자세한 내용은 `04_시나리오_실행법.md` 부록) |
| `SUCCESS`인데 로봇이 안 움직인다 | `planned_points=0`이면 이미 목표 자세에 있다는 뜻(정상). 다른 자세를 목표로 준다: `--named extended` |
| MoveIt이 `START_STATE_IN_COLLISION(-10)`을 낸다 | 직접 제어(`joint_command.py`·`leader_follow.py`)가 팔을 자기충돌 자세로 두었다. MoveIt은 그 자세에서 계획을 시작할 수 없다(정상 동작). `group_goal_client.py`가 닿은 링크와 복구 명령을 출력한다: `joint_command.py --named rest --time 3` 후 다시 계획 |
| `ros2 control list_controllers`가 30초 멈추고 빈 결과 | ros2cli 데몬이 자기 RPC 주소를 `127.0.0.1`로 고정하기 때문(`ros2cli/daemon/__init__.py`). mirrored 환경에서는 우회 불가. **`./scripts/04_smoke_test.sh`가 같은 정보를 서비스 직접 호출로 보여준다.** 근본 해결은 `.wslconfig`의 `networkingMode=mirrored` 제거 |
| `ros2 daemon status`/`stop`이 멈춘다 | 위와 같은 원인. 이 프로젝트 스크립트는 데몬에 의존하지 않으므로 그냥 쓰지 않으면 된다 |
| `ros2 node list`에 노드가 일부만 보인다 | 우회 프로필의 유니캐스트 탐색 특성. 토픽·서비스·액션 기능은 정상이다(`04_smoke_test.sh`로 확인). 완전한 목록이 필요하면 `.wslconfig` 수정 |
| 위 방법으로도 안 되면 | PowerShell에서 `wsl --shutdown` 후 `wsl -d Ubuntu`. 재시작 후 `07_doctor.sh`로 통신을 먼저 확인하고 bringup |
| GUI 창이 안 뜬다 | WSLg 확인: `echo $DISPLAY`(`:0`), `glxinfo -B`. 창 문제만 분리하려면 `mujoco_headless:=true`로 돌려 본다 |
| spawner가 `controller_manager` 못 찾고 타임아웃 | 컨트롤러 매니저 노드가 죽은 것. 터미널 1의 로그를 본다. `mujoco`인데 `mujoco_model` 경로가 틀리면 여기서 죽는다 |
| Plan은 되는데 Execute가 안 됨 | `moveit_controllers.yaml`의 컨트롤러 이름·`action_ns`와 `ros2 action list -t` 비교. 컨트롤러가 `active`인지 확인 |
| "robot state is not up to date" | `/joint_states` 발행자가 0개이거나 2개. `use_sim_time`이 노드마다 다른 경우도 이 증상 |
| 팔이 두 자세 사이를 오감 | 같은 컨트롤러에 두 곳(RViz + 슬라이더 등)에서 명령. 하나만 사용 |
| RViz에 Planning Group이 안 보임 | MoveIt config 패치 실패. `grep -rn manipulator ~/so101_ws/src/so101_project_moveit_config`가 0건이어야 한다 |
| MuJoCo 팔이 진동·폭주 | `mjcf/so101.xml`의 actuator `kp`를 낮추고, `option timestep`을 줄여 본다 |
| MuJoCo에 놓은 상자를 MoveIt이 무시함 | 정상. **MoveIt Planning Scene에 같은 상자를 따로 등록해야 한다** |

로그와 버전 기록:

```bash
cat ~/so101_ws/artifacts/versions.txt
cat ~/so101_ws/log/latest_build/*/stderr.log | head -40
```

## 8. 한 줄 용어 사전

- **워크스페이스**: 빌드해서 `ros2`가 찾을 수 있게 만드는 폴더(`~/so101_ws`). MoveIt이 아니라 ROS 2/colcon 개념.
- **Planning Group**: 함께 계획할 관절 묶음(`arm`=팔 5관절, `gripper`=1관절). 네트워크 그룹이 아니다.
- **액션(action)**: 오래 걸리는 요청을 진행상황·결과와 함께 처리하는 ROS 통신. `Plan & Execute`가 이걸 쓴다.
- **spawner**: 컨트롤러를 컨트롤러 매니저에 올려 `active`로 만드는 유틸.
- **mock**: 물리 없이 명령을 그대로 상태로 되돌려주는 가짜 하드웨어. 배선 검증용.
- **keyframe**: MJCF에 저장된 자세. `rest`로 시작하면 팔이 접힌 자세에서 출발한다.
- **bringup**: 로봇을 실행 상태로 올리는 launch. 터미널을 계속 점유하며, 이때부터 로봇이 "켜진" 상태다.
