### 1-2. 검증한 사실 (문서·업스트림·실행)

- `mujoco_ros2_control`은 ros-controls 공식 패키지이고 Humble·Jazzy·Kilted·Rolling을 Supported로 명시. 플러그인 이름 `mujoco_ros2_control/MujocoSystemInterface`, 파라미터 `mujoco_model`, **전용 `ros2_control_node` 필요**.
- 공식 데모 launch(`01_basic_robot.launch.py`) 노드 구성을 그대로 확인 → 우리 `bringup.launch.py`가 같은 패턴(전용 노드 + `ParameterFile` + spawner `--param-file` + Humble 전용 remap)이다.
- URDF→MJCF 변환기는 `robot_description_to_mjcf.sh` / `make_mjcf_from_robot_description.py`, 옵션 `-u -o --save_only --add_free_joint -c --fuse -a`, 문서에 "hacky and _highly_ experimental" 경고.
- 업스트림 `legalaspro/so101-ros-physical-ai`: `hardware_type`은 `real`/`mock`이고 **`mujoco`는 planned(미지원)**. `so101_moveit_config`는 완성된 MSA 패키지(SRDF·pick_ik·OMPL·Pilz·launch 3종). `feetech_ros2_driver`는 서브모듈.
- `ycheng517/lerobot-ros`: Jazzy만 테스트, `requires-python >=3.10`, **`lerobot>=0.4.0,<0.5.0` 핀** (최신 LeRobot 0.6.x와 섞으면 깨진다).

### 1-3b. MuJoCo 모델은 변환하지 않고 공식 모델을 가져왔다

MuJoCo Menagerie의 **`robotstudio_so101`**(Apache-2.0)이 우리 URDF와 **관절 이름·범위가 일치**하고
**position actuator 6개가 이미 정의**되어 있어서, 실험적 URDF→MJCF 변환기 대신 이 모델을 프로젝트에 넣었다.

```
joint          MJCF joint range        actuator ctrlrange     URDF 대조
shoulder_pan   -1.91986   1.91986      -1.91986  1.91986      일치
shoulder_lift  -1.7453293 1.7453293    -1.74533  1.74533      일치
elbow_flex     -1.69      1.69         -1.69     1.69         일치
wrist_flex     -1.658063  1.658063     -1.65806  1.65806      일치
wrist_roll     -2.7438473 2.84121 (*)  -2.74385  2.84121      (*) 상한을 URDF에 맞춰 수정
gripper        -0.174533  1.7453292    -0.17453  1.74533      일치
```

손본 것 2가지:
1. **wrist_roll joint range 상한** 2.7438473 → 2.84121. 안 고치면 MoveIt이 2.8을 계획했을 때
   시뮬레이터가 클램프해 추종오차처럼 보인다.
2. **`keyframe name="rest"` 추가** (`qpos="0 -1.57 1.57 0.75 0 0"`, SRDF `rest`와 동일 자세).
   `bringup.launch.py`의 `mujoco_keyframe:=rest`(기본값)가 이 자세로 시작하게 한다.

출처·라이선스·주의사항은 `src/so101_project/mjcf/README.md`.

```bash
# 5) 모델 확인
source ~/so101_ws/install/setup.bash
./scripts/02_export_urdf.sh
```

### Mock으로 그룹 제어 먼저 성공시키기 (블로그 13편 대응)

`bringup`은 터미널을 계속 점유하는 실행 프로세스다. **터미널 2개를 각각 따로** 쓴다
(한 터미널에 두 블록을 통째로 붙여넣으면 엉킨다).

터미널 1 — 계속 점유:

```bash
./scripts/06_bringup.sh mock
```

터미널 2:

```bash
./scripts/04_smoke_test.sh
```

합격 기준: 컨트롤러 3개 active · `/joint_states` 발행자 1개 · RViz Planning Group에 `arm`/`gripper` ·
`group_goal_client.py --group arm --named rest` plan-only 성공 · 그룹 외 관절 요청은 거부.

터미널 2에서 실제로 움직여 보기 (mock이라 물리 없음, 값만 이동):

```bash
ros2 run so101_project group_goal_client.py --group arm --named rest --execute --vel 0.1
ros2 run so101_project group_goal_client.py --group gripper --named closed --execute
```

### MuJoCo로 물리 검증 (블로그에 없는 신규 작업)

**모델은 이미 들어 있다**(`src/so101_project/mjcf/scene.xml`, 1-3b절). 변환 작업이 필요 없다.

터미널 2(또는 bringup 전에):

```bash
./scripts/03_make_mjcf.sh      # 모델 점검: 관절·actuator·범위 표 출력
```

터미널 1 — MuJoCo 창 + RViz 창이 함께 열리고 `rest` keyframe 자세에서 시작한다:

```bash
./scripts/06_bringup.sh mujoco
```

터미널 2:

```bash
./scripts/04_smoke_test.sh     # 이번에는 /clock 이 나오고 use_sim_time=true 여야 한다
ros2 run so101_project group_goal_client.py --group arm --named rest --execute --vel 0.1
```

합격 기준: **계획 → actuator 명령 → 물리 step → 측정 state** 흐름으로 관절이 움직이고,
클라이언트가 출력하는 실측 오차가 허용치 안. (qpos를 외부에서 덮어써 움직이는 것은 합격이 아니다.)

옵션: `mujoco_headless:=true`(창 없이), `mujoco_keyframe:=""`(0 자세에서 시작),
`scene_box.xml`(상자가 있는 씬 — 단, MoveIt Planning Scene에도 같은 상자를 등록해야 충돌 회피가 맞는다).

### 화면 보면서 제어하기 · 사진 찍기

실물이 없어도 **로봇이 움직이는 화면**을 3종류 얻을 수 있다. WSLg 창이므로 Windows 캡처 도구
(`Win`+`Shift`+`S`)로 그대로 찍힌다.

| 창 | 무엇이 보이나 | 띄우는 법 |
|---|---|---|
| **MuJoCo Simulate** | 메시가 붙은 SO-101이 중력·접촉과 함께 물리로 움직인다. 가장 "시뮬레이터답게" 보이는 화면 | `bringup.launch.py hardware_type:=mujoco` (기본 `mujoco_headless:=false`) |
| **RViz2 + MotionPlanning 패널** | Planning Group(`arm`/`gripper`) 선택, 인터랙티브 마커 드래그, `Plan` → 경로 애니메이션 → `Execute` | bringup의 `use_rviz:=true`(기본) |
| **rqt_joint_trajectory_controller** | 관절별 슬라이더. 움직이면 JTC로 궤적이 나가 MuJoCo 팔이 따라온다 | `./scripts/05_gui.sh sliders` |

가장 빠른 길 — **ROS·빌드 없이 지금 당장** 모델만 띄워 사진 찍기:

```bash
./scripts/05_gui.sh viewer      # venv에 pip mujoco 설치 후 scene.xml 을 뷰어로 열어준다
```

그 외:

```bash
./scripts/05_gui.sh rqt         # 컨트롤러 상태(rqt_controller_manager) + 노드 그래프
./scripts/05_gui.sh foxglove    # 브라우저로 보기: app.foxglove.dev → ws://localhost:8765
```

**제어 방법 3가지의 차이를 알고 쓸 것:**

| 방법 | MoveIt 계획·충돌검사 | 용도 |
|---|---|---|
| RViz MotionPlanning 패널 | **거친다** | 계획 결과를 눈으로 확인하며 시연 |
| `group_goal_client.py` | **거친다** | 재현 가능한 검증·자동화, 실패 원인 구분 |
| rqt 슬라이더 / LeRobot 키보드 텔레옵 | **거치지 않는다**(컨트롤러 직접) | 하드웨어·컨트롤러 자체 확인, 손맛 있는 시연 |

같은 컨트롤러에 두 방법이 동시에 명령을 보내지 않게 한 번에 하나만 쓴다.

사진용 추천 시나리오: ① `05_gui.sh viewer`로 모델 단독 → ② `hardware_type:=mock` + RViz에서
Plan/Execute → ③ `hardware_type:=mujoco` + RViz + 슬라이더 3창을 나란히 배치.

### LeRobot 어댑터로 텔레옵까지 시뮬레이터에서 (선택, 블로그 15편 선행)

```bash
python3 -m venv --system-site-packages ~/venvs/so101-lerobot-ros
source ~/venvs/so101-lerobot-ros/bin/activate
source /opt/ros/jazzy/setup.bash && source ~/so101_ws/install/setup.bash

pip check && python -c 'import rclpy, lerobot; print("ok")'
```

어댑터 config를 우리 컨트롤러에 맞춘다 (`ActionType.JOINT_TRAJECTORY`,

**Gazebo launch는 실행하지 않는다.** 그 다음:

"텔레옵 성공"과 "Planning Group 계획 성공"은 별개로 검증한다. 또 MoveIt 실행 중에 어댑터가
같은 컨트롤러로 명령을 계속 보내지 않게 실행 모드를 나눈다.

## 3. 집에 가서 실물 연결 후 할 일

### 3-0. 순서 요약

```
USB 전달 → 포트 확인 → (LeRobot 캘리브레이션 확인/필요시 재보정)
→ 현재 자세 읽기 → sign/offset 확정 → 단일 관절 저속 시험
→ 그리퍼 → arm 그룹 실행 → 외부 클라이언트 → (선택) 텔레옵·기록
```

**절대 순서를 바꾸지 말 것:** 업스트림 README는 "ROS 2로 실물 팔을 명령하기 전에 LeRobot 모터 설정과
캘리브레이션을 먼저 완료해야 한다"고 요구한다(EEPROM에 ID·캘리브레이션 값이 기록된다).

### 3-1. USB를 WSL로 전달

```powershell
# 한 번만
winget install --interactive --exact dorssel.usbipd-win

# 로봇 전원·USB 연결 후, 관리자 PowerShell
usbipd list
usbipd bind --busid <실제 BUSID>      # 예: 4-4
usbipd attach --wsl --busid <실제 BUSID>
```

```bash
# WSL(24.04)에서
lsusb
ls -l /dev/serial/by-id/ /dev/ttyACM* /dev/ttyUSB* 2>/dev/null
sudo usermod -aG dialout "$USER"      # 이후 새 로그인 세션에서 id -nG 로 확인
```

Windows COM 번호와 WSL tty 번호는 다르다. 장치를 뽑았다 끼우면 `attach`를 다시 해야 한다.

### 3-2. LeRobot 하드웨어 환경 (기존 캘리브레이션 우선 보존)

```bash
# --system-site-packages: 이 환경에서 rclpy(ROS)도 import 되어야 한다.
# leader_follow.py --source lerobot 이 한 프로세스 안에서 lerobot 과 rclpy 를 같이 쓴다.
python3 -m venv --system-site-packages ~/venvs/so101-hardware
source ~/venvs/so101-hardware/bin/activate
source /opt/ros/jazzy/setup.bash && source ~/so101_ws/install/setup.bash
pip install -U pip
pip install 'lerobot[core_scripts,feetech]' evdev      # WSL은 evdev 필요 (공식 문서 명시)
mkdir -p ~/so101_ws/artifacts
pip freeze > ~/so101_ws/artifacts/lerobot_hardware_freeze.txt

python -c 'import lerobot, rclpy; print("lerobot", lerobot.__version__, "+ rclpy OK")'
lerobot-find-port            # 포트 확인
```

2026-09-09 기준 24.04 배포판에는 **LeRobot이 아직 설치돼 있지 않다**(Python 3.12.3이라 0.5+ 설치 가능).
시뮬레이터 미션 1·2·3은 LeRobot 없이 되므로, 이 설치는 실물을 붙일 때 하면 된다.

- **이미 텔레옵을 해봤다면 `setup-motors`를 다시 실행하지 않는다.** 모터 ID는 이미 기록돼 있다.
- 이전 환경의 캘리브레이션 파일이 있으면 그 로봇 id로 복사해 온다. 설치된 LeRobot 버전이 쓰는 디렉터리를 먼저 확인한다.
- 조립·영점이 바뀌었을 때만 재보정:

```bash
lerobot-calibrate --robot.type=so101_follower --robot.port=/dev/ttyACM0 --robot.id=my_so101_follower
```

### 3-3. 기존 LeRobot 텔레옵으로 하드웨어 자체를 먼저 확인 (권장)

ROS를 붙이기 전에 **로봇이 정상인지**를 익숙한 방법으로 확인한다. 리더까지 연결했다면:

```bash
lerobot-teleoperate --help     # 설치 버전의 정확한 플래그 확인 후 사용
lerobot-teleoperate \
  --robot.type=so101_follower --robot.port=/dev/ttyACM0 --robot.id=my_so101_follower \
  --teleop.type=so101_leader  --teleop.port=/dev/ttyACM1 --teleop.id=my_so101_leader
```

> 블로그 연재에는 leader-follower 텔레옵 편이 따로 없다(15편이 LeRobot Record/Replay). 텔레옵은
> 원래 LeRobot 쪽 기능이므로 기존에 하던 방식을 그대로 쓰면 된다.

**확인이 끝나면 이 프로그램을 반드시 종료한다.** LeRobot과 ROS Feetech 드라이버가 같은 USB 포트를
동시에 열 수 없다.

### 3-4. ROS 실물 백엔드 연결

```bash
source /opt/ros/jazzy/setup.bash && source ~/so101_ws/install/setup.bash

# 실물 드라이버 빌드 (libserial-dev 설치까지 한 번에)
cd <저장소 루트>          # 예: cd ~/edu_lerobot_mujoco_moveit2_ros2
./scripts/01_setup_workspace.sh --with-real
source ~/so101_ws/install/setup.bash

# 서브모듈이 빠져 있었다면
git -C ~/so101_ws/vendor/so101-ros-physical-ai submodule update --init --recursive
./scripts/01_setup_workspace.sh --with-real
```

1. **읽기 먼저.** 로봇 전원을 켠 상태에서 아래를 띄우고, 손으로 움직이지 않은 채 `/joint_states`가
   현재 자세를 그대로 반영하는지 본다. RViz 자세와 실물 자세가 다르면 여기서 멈추고 sign/offset을 고친다.

터미널 1:

```bash
./scripts/06_bringup.sh real usb_port:=/dev/ttyACM0 launch_moveit:=false
```

터미널 2:

```bash
ros2 topic echo /joint_states --once --no-daemon
ros2 control list_hardware_interfaces
```

2. `src/so101_project/config/joint_mapping.yaml`의 `sign`/`offset_rad`를 **한 관절씩** 채운다.
   기준: `q_ros = sign * q_motor_rad + offset_rad`. 관절 하나에 +0.1 rad를 주고 실제 회전 방향을 확인한다.

3. **모터 명령 초기값은 0이 아니라 "읽은 현재 위치"** 여야 한다. 첫 명령이 큰 점프가 되지 않게 확인한다.

4. 가까운 목표부터, 아주 느리게:

터미널 1:

```bash
./scripts/06_bringup.sh real usb_port:=/dev/ttyACM0
```

터미널 2:

```bash
ros2 run so101_project group_goal_client.py --group gripper --named open --execute --vel 0.05
ros2 run so101_project group_goal_client.py --group arm --named rest --execute --vel 0.05 --acc 0.05
```

5. 취소·timeout·장치 분리 동작을 일부러 만들어 확인한다(USB 뽑기, Ctrl-C).

**안전:** 종료·이상 시 로봇을 지지하거나 전원을 끊을 수 있는 상태에서 시작한다. 스케일링(0.05)은
URDF/MoveIt 한계에 곱하는 값이라 한계 자체가 잘못되면 안전을 보장하지 못한다.

### 3-5. (선택) 실물 + LeRobot 데이터 파이프라인 (블로그 15편 대응)

## 4. 문제가 생겼을 때 (계층별 진단 — 블로그 16편 구조 차용)

WebSocket 계층이 없으므로 4계층은 **MoveIt → 컨트롤러 → 하드웨어 인터페이스 → USB**다.

| 증상 | 어느 계층 | 먼저 볼 것 |
|---|---|---|
| RViz에 모델이 안 보임 | 모델 | `ros2 run xacro xacro ...` 단독 성공 여부, mesh 경로(workspace source 여부) |
| Planning Group이 안 보임 | MoveIt | SRDF 치환 결과(`grep -r manipulator` 0건인지), `/robot_description_semantic` 발행 여부 |
| Plan 성공, Execute 실패 | MoveIt↔컨트롤러 | `moveit_controllers.yaml`의 이름/`action_ns`와 `ros2 action list -t` 비교, 컨트롤러 active 여부 |
| "robot state is not up to date" | 컨트롤러 | `/joint_states` 발행자 수, timestamp, `use_sim_time` 일치 |
| 로봇이 두 자세를 오감 | 컨트롤러 | `joint_state_publisher_gui`나 두 번째 controller_manager가 살아있는지 |
| MuJoCo가 진동/폭주 | 하드웨어 인터페이스(MJCF) | actuator kp, timestep, 질량·관성, 초기 자세 충돌 |
| MuJoCo는 안 움직이는데 RViz만 움직임 | 하드웨어 인터페이스 | 전용 `ros2_control_node`를 썼는지(mock 노드가 아닌지), `mujoco_model` 경로 |
| 말단 목표 IK 계속 실패 | MoveIt | 5자유도 한계. 관절 목표/저장 자세로 먼저 검증, `rotation_scale` 조정 |
| 그리퍼만 이상 | 모델/단위 | rad·degree·0–100 정규화 혼용 여부, `open=1.5`/`closed=-0.16` 기준 |
| 실물만 방향 반대 | USB/매핑 | `joint_mapping.yaml`의 `sign`, 모터 ID 매핑 |
| 장치가 안 보임 | USB | `usbipd bind/attach`, `lsusb`, dialout 그룹 |
| LeRobot에서 rclpy import 실패 | 환경 | Python 3.12/ROS source/venv 혼용, 어댑터의 lerobot 0.4.x 핀 |
| `ros2 control ...`이 멈추거나 `TimeoutError: [Errno 110]` | ROS CLI | ros2cli 데몬이 응답하지 않음. `ros2 daemon stop` 후 조회는 `--no-daemon` |
| 로그에는 컨트롤러가 active인데 다른 터미널에서 아무것도 안 보임 | WSL | **`./scripts/07_doctor.sh --fix`** 실행. 배경은 `04_시나리오_실행법.md` 부록 |
| bringup이 `Waiting for data on 'robot_description'`을 반복 | WSL | 같은 원인(고아 SHM 세그먼트 등). `07_doctor.sh --fix` 후 bringup 재실행 |

버전 기록은 항상 남긴다.

```bash
cd ~/so101_ws
dpkg-query -W 'ros-jazzy-*' > artifacts/ros_packages.txt
git -C vendor/so101-ros-physical-ai rev-parse HEAD > artifacts/so101_upstream_commit.txt
```
