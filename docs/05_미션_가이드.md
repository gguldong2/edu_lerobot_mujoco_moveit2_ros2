# 미션 가이드 — 블로그 9·10·13편을 MuJoCo + MoveIt2로 재현하고 녹화하기

> 이 문서의 모든 명령은 **저장소 루트에서** 실행한다 (`cd <클론한 폴더>`).
> `ros2 run so101_project X` 형태는 터미널 준비가 끝난 상태를 가정한다(0-3절).
> 준비 없이 쓰려면 `./scripts/08_run.sh X`를 쓴다.

이 문서는 "무엇을 실행하면 무엇이 보이고, 어디를 찍으면 되는지"만 다룬다.
개념 설명은 `03_사용법.md`, 시나리오별 배경은 `04_시나리오_실행법.md`,
블로그와의 대응·의사결정은 `01_작업계획서_블로그대응_및_의사결정.md`에 있다.

세 미션은 서로 다른 것이 아니라 **같은 배선의 서로 다른 입구**다.

```
 미션1  leader(사람/데모/실물)  →  leader_follow.py   ┐
 미션2  사람이 각도를 지정      →  joint_command.py    ├→ arm_controller / gripper_controller (JTC)
 미션3  MoveIt 계획            →  RViz / group_goal_client.py ┘            │
                                                                          ▼
                                                       ros2_control 하드웨어 인터페이스
                                                        mock  │  mujoco  │  real
                                                                          │
                                            joint_state_broadcaster → /joint_states → RViz 모델
```

입구는 셋이지만 출구(컨트롤러 → 하드웨어 → 상태 발행 → RViz)는 하나다.
그래서 미션 1·2·3의 명령은 **mock에서 되면 MuJoCo에서도, 실물에서도 글자 하나 안 바꾸고 된다.**

### 0-1. 통신 문제 처리 — 둘 중 하나만 하면 된다

이 랩탑은 WSL의 `networkingMode=mirrored` 때문에 **127.0.0.1 통신 자체가 죽어 있다.**
그것이 지금까지 본 `Waiting for data on 'robot_description' topic` 반복과
`ros2 daemon ... TimeoutError`의 진짜 원인이다.
(측정 근거는 `04_시나리오_실행법.md` 부록에 그대로 적어 두었다)

- **(A) 그냥 쓰기** — 이 프로젝트의 `04·05·06·07` 스크립트가 우회를 자동으로 적용한다.
  아무것도 하지 않아도 된다. 스크립트를 실행하면 아래 한 줄이 먼저 보인다:
  ```
  [dds] 127.0.0.1 이 죽어 있다(WSL mirrored). DDS 를 10.255.255.254 로 우회한다: /tmp/so101_fastdds_...xml
  ```
  단, **직접 만든 터미널에서 `ros2` 명령을 쓸 때**는 그 터미널에도 같은 설정이 필요하다:
  ```bash
  source scripts/env.sh
  ```
  (0-3에서 이 줄을 `~/.bashrc`에 넣으면 새 터미널마다 자동으로 적용된다)
  (귀찮으면 (B)를 하면 이 줄이 영구히 필요 없어진다)

  **우회로 다 되지만, 두 가지는 안 된다** (127.0.0.1을 쓰는 것이 ROS 쪽이 아니라 CLI 도구라서):

  | 안 되는 것 | 대신 |
  |---|---|
  | `ros2 control list_controllers` (30초 멈춘 뒤 빈 결과) | `./scripts/04_smoke_test.sh` — 같은 정보를 서비스 직접 호출로 보여준다 |
  | `ros2 daemon status/stop` (멈춤) | 필요 없다. 스크립트가 알아서 처리한다 |
  | `ros2 node list`가 일부만 보임 | 기능(토픽·서비스·액션)은 정상이다. 목록은 `04_smoke_test.sh`로 본다 |

  이유: `ros2cli`의 데몬은 자기 RPC 주소를 `127.0.0.1`로 **소스에 고정**해 두었다
  (`ros2cli/daemon/__init__.py`). DDS를 우회해도 이 채널은 우회할 수 없다.
  **그래서 아래 (B)를 권한다.**

- **(B) 근본 해결 (권장)** — Windows 쪽 설정 한 줄:
  1. 메모장으로 `C:\Users\<사용자>\.wslconfig` 열기
  2. `networkingMode=mirrored` 줄을 지우거나 앞에 `#` 붙이기 (= 기본 NAT 모드로 돌아간다)
  3. PowerShell에서 `wsl --shutdown` → 터미널 다시 열기
  4. `./scripts/07_doctor.sh` 실행 → **4번 항목이 `[OK] 127.0.0.1 UDP 왕복 정상`**이면 끝
  - mirrored 모드를 Windows↔WSL의 localhost 접속 때문에 일부러 쓰고 있었다면 (A)로 두면 된다.
    로봇 쪽 기능 차이는 없다.

### 0-3. 터미널 준비를 영구화 (이걸 하면 `ros2: command not found`가 사라진다)

새 터미널에는 ROS 환경이 없다. 그래서 아무 준비 없이 `ros2 run ...`을 치면

- **(A) 한 번만 설정** — 새 터미널마다 자동 준비 (권장)

  ```bash

  exec bash        # 지금 터미널에도 바로 적용
  ```

  이후로는 `ros2 run so101_project leader_follow.py ...`를 그냥 쓸 수 있다.
  (이 한 줄이 ROS + 워크스페이스 + WSL 통신 우회 세 가지를 다 한다)

- **(B) 그때그때** — 래퍼로 실행 (아무 준비 없이 바로 됨)

  ```bash
  ./scripts/08_run.sh leader_follow.py --source demo
  ./scripts/08_run.sh ros2 control list_controllers      # ros2 명령도 통과시킨다
  ```

아래 미션들의 명령은 **(A)를 한 상태**를 가정한 `ros2 run` 형태로 적었다.
(A)를 안 했으면 `ros2 run so101_project` 자리를 `./scripts/08_run.sh`로 바꿔 읽으면 된다.

또 노드 파일을 새로 추가한 뒤에는 한 번 빌드해야 링크가 생긴다(이미 해 두었다):

### 1-1. 무엇을 보면 정상인가 (세 미션 공통)

창 두 개와 터미널이 각각 다른 것을 보여준다. **합격/불합격은 화면이 아니라 터미널 숫자로 판정한다.**
화면은 "무슨 일이 일어나는지"를 보여주는 촬영용이다.

| 미션 | MuJoCo 창 (물리) | RViz (모델·계획) | 터미널 (판정) |
|---|---|---|---|
| 1 (추종) | 팔이 **계속** 부드럽게 움직인다 | 같은 움직임을 모델이 따라간다 | 0.5초마다 상태줄, `최대추종오차` |
| 2 (직접 명령) | 명령한 관절만 `--time` 동안 움직이고 멈춘다 | 같이 움직인다 | `SUCCESSFUL` + 목표/실측 오차 표 |
| 3 (MoveIt) | **RViz의 Execute를 누른 뒤에** 움직인다 (Plan만 누르면 안 움직인다) | **주황색 목표 자세 + 반투명 경로 재생**(이게 미션 3에만 있다) | `error_code=SUCCESS` + `planned_points`(0이면 이미 도착) + `worst error` |

> 미션 3의 "Execute"는 **RViz 패널의 버튼**이다. MuJoCo 창에는 로봇에 명령하는 버튼이 없다
> (물리 뷰어다). 명령줄에서는 `--execute` 옵션이 그 버튼과 같은 역할을 한다.

핵심은 이것이다.

- **RViz는 세 미션 모두에서 움직인다.** RViz가 그리는 것은 계획이 아니라 `/joint_states`
  (= 실제 측정값)이기 때문이다. 미션 3에만 있는 것은 **실행 전 미리보기**(반투명 경로)다.
- **물리는 MuJoCo 창에서만 일어난다.** 중력에 처지고 물체에 부딪히는 것은 여기서만 보인다.
- 두 창이 **같은 자세**를 보여야 정상이다. 어긋나면 아래로 판단한다.

| 증상 | 뜻 |
|---|---|
| **터미널은 `SUCCESS`인데 두 창이 다 가만히 있다** | 목표가 지금 자세와 같다. `planned_points=0`이면 움직일 것이 없다는 뜻이고 **정상**이다. 다른 자세를 목표로 준다(4-2) |
| MuJoCo는 움직이는데 RViz가 가만히 있다 | `/joint_states`가 RViz까지 안 간다 → 통신 문제 (`07_doctor.sh`) |
| 터미널은 `SUCCESSFUL`인데 MuJoCo가 안 움직인다 | `mock` 백엔드로 떠 있다 (`06_bringup.sh mujoco`인지 확인) |
| RViz에 로봇이 아예 안 보인다 | `/robot_description`을 못 받은 것. bringup 로그를 본다 |
| 둘 다 움직이는데 오차가 크다 | 요구 속도가 너무 빠르다 → `--time`을 늘리거나 `--vel`을 낮춘다 |

### 1-2. 숫자 읽는 법 — 두 미션이 재는 것이 다르다

미션 1과 미션 2·3은 **다른 종류의 오차**를 본다. 같은 "오차"라는 말이지만 뜻이 다르다.

| | 미션 1 `최대추종오차` | 미션 2·3 `최대 오차` / `worst error` |
|---|---|---|
| 언제 재나 | **움직이는 중에** 계속 (0.5초마다) | **다 멈춘 뒤에** 한 번 |
| 무엇과 무엇의 차이 | 방금 보낸 명령 ↔ 지금 실제 각도 | 최종 목표 ↔ 최종 실제 각도 |
| 0이 될 수 있나 | **아니다.** 움직이는 동안은 항상 뒤처진다 | **거의 0이 되어야 한다** |
| 커지면 뜻 | 요구 속도가 로봇 능력보다 빠르다 | 목표에 도달하지 못했다 (문제 신호) |

#### 미션 1 (추종): 0이 아닌 게 정상이다

스트리밍 제어는 "0.15초 뒤에 여기 있어라"를 30번/초 보낸다(`--lookahead`). 로봇은 그 목표로
가는 도중에 다음 목표를 받으므로 **항상 조금 뒤처진 상태로 따라온다.** 그 뒤처진 양이 추종오차다.

| 값 | 판정 |
|---|---|
| 0.03 ~ 0.15 rad (2~9°) | **정상.** 부드럽게 따라오고 있다 |
| 0.2 rad (11°) 이상 | 너무 빠르게 요구하는 것. `--period`를 늘리거나 `--amplitude`를 줄인다 |
| 계속 커진다 | 명령을 못 따라가고 있다. `--max-vel`을 낮춘다 |
| mock과의 비교 | 느린 동작에서는 둘 다 0.1 rad 근처다(지연분이 지배적이다). 빠르게 요구할 때 MuJoCo에서 크게 벌어진다 — `--period 5 --amplitude 0.5`에서 0.38 rad까지 확인했다. **이 차이가 물리 시뮬레이션의 값이다** |

#### 미션 2·3 (목표 도달): 거의 0이어야 한다

| 백엔드 | 기대값 | 이유 |
|---|---|---|
| `mock` | 정확히 0.0000 | 물리가 없다. 명령을 그대로 반사한다 |
| `mujoco` (시간 여유 있게) | 0.001 rad 이하 (0.06° 이하) | 위치 제어가 목표에 정착한다 |
| `mujoco` (`--time`이 짧으면) | 0.01 rad 수준 | 정착할 시간이 부족하다 |
| `real` (집에서) | 0.01~0.05 rad (0.5~3°) 예상 | 서보 분해능·백래시·중력 처짐 |

#### 표에서 어디를 보나 (미션 2)

```
  관절            목표(rad)    실측(rad)     오차(rad)
  elbow_flex     +1.5650     +1.5654     +0.0005     ← 명령 안 한 관절: 현재 자세 유지
  shoulder_lift  -1.5949     -1.5948     +0.0000     ← 명령 안 한 관절: 현재 자세 유지
  shoulder_pan   +0.5236     +0.5236     +0.0000     ← 내가 명령한 관절 (30도)
  최대 오차 0.0005 rad (0.03 deg)                     ← 판정 숫자
```

1. **`실행 완료: SUCCESSFUL`** — 1차 판정. 컨트롤러가 궤적을 끝까지 실행하고 허용오차를
   위반하지 않았다는 뜻이다. `GOAL_TOLERANCE_VIOLATED`가 나오면 도달하지 못한 것이다.
2. **내가 명령한 관절의 행** — 목표와 실측이 같은지. 이게 "명령이 통했나"다.
3. **명령하지 않은 관절의 행** — 이 노드는 지정하지 않은 관절에 **현재 자세를 그대로** 목표로
   넣는다(다른 관절이 0으로 튀지 않게). 그래서 목표=현재값이고 오차가 작아야 한다.
   **여기가 크면 다른 무언가가 동시에 로봇을 명령하고 있다는 신호다**(예: `leader_follow.py`가
   아직 돌고 있다, 슬라이더 창이 열려 있다).
4. **`최대 오차`** — 전체 중 가장 큰 값. 위 표와 비교해 판정한다.

## 2. 미션 1 — leader를 움직이면 follower가 따라오고 RViz도 움직인다 (블로그 9편)

### 2-0. "추종"이 무슨 말인가 · 언제 끝나나

**추종(following)** = leader 팔을 사람이 손으로 움직이면, follower 팔이 그 각도를 흉내내며
따라오는 것. 블로그 9편의 그 장면이다. 사람이 목표를 계획하지 않고 **손으로 직접 끌고 다니는**
제어라서, MoveIt의 계획·충돌검사가 개입하지 않는다.

```
사람 손 → leader 각도 → (30번/초) → follower 컨트롤러 → 팔이 그 자세로
                                                        └→ /joint_states → RViz
```

- **끝나는 조건**: 기본은 **무한**이다. `Ctrl`+`C`를 누를 때까지 계속 돌고, 멈추면 마지막
  명령 자세에 그대로 선다(원위치로 돌아가지 않는다).
- 정해진 시간만 돌리려면 `--duration 10`(초). 데모의 왕복 주기는 `--period`(기본 8초)다.
- **여기서 볼 것 두 가지**: ① 두 창(MuJoCo·RViz)이 같은 자세로 함께 흐르는가
  ② 터미널의 `최대추종오차`가 안정적인가 (1-2절의 판정표)

명령은 **한 줄이면 된다.** 앞에서 여러 형태를 보여준 것은 *같은 일을 하는 다른 방법*이었다.

| 쓴 형태 | 뜻 |
|---|---|
| `./scripts/08_run.sh leader_follow.py --source demo` | 환경 준비까지 알아서 하고 추종 실행 |
| `ros2 run so101_project leader_follow.py --source demo` | **위와 완전히 같다.** `~/.bashrc`에 `env.sh`를 넣은 뒤에는 이 형태를 쓴다 |
| `./scripts/08_run.sh ros2 topic echo /joint_states --once` | 추종과 무관한 예시. 래퍼로 `ros2` 명령도 쓸 수 있다는 것을 보인 것 |

### 2-1. 블로그와 우리 환경의 차이

| 항목 | 블로그 9편 | 이 프로젝트 | 이유 |
|---|---|---|---|
| leader | 실물 leader 암 (USB) | **데모 신호 / 슬라이더 / 실물 leader** 셋 중 선택 | 실물이 없어도 같은 경로를 보여줘야 한다 |
| follower | 실물 follower 암 | **MuJoCo 물리 모델** (또는 mock/실물) | Unreal → MuJoCo 치환의 핵심. 중력·마찰이 있는 진짜 추종을 본다 |
| 상태 발행 | `robot_status_publisher` 노드를 직접 작성 | **`joint_state_broadcaster`** (ros2_control 표준) | 상태 소스를 컨트롤러와 하나로 묶는다 (문서 01 대응표 (8)(9)) |
| RViz 동기화 | 위 노드가 `/joint_states` 발행 | 동일한 `/joint_states`를 broadcaster가 발행 | RViz 쪽 설정은 블로그와 같다 |
| leader→follower 전달 | LeRobot 텔레옵이 서보에 직접 씀 | **`leader_follow.py` → JTC 궤적 토픽** | 같은 명령 경로를 MoveIt과 공유해야 mock/MuJoCo/실물이 같아진다 |
| 안전장치 | (없음) | URDF 한계 clamp + `--max-vel` 속도 제한 + `--print-only` | leader를 갑자기 휘둘러도 명령은 제한된다 |

한 줄 요약: **블로그의 "실물 leader → 실물 follower → RViz"에서 follower 자리에 MuJoCo를 넣은 것**이다.

### 2-2. 방법 A — 하드웨어 없이 바로 녹화 (지금 가능, 제일 쉽다)

`--source demo`는 내장 사인파를 leader로 쓴다. 현재 자세를 중심으로 부드럽게 흔든다.

```bash
# 터미널 1: ./scripts/06_bringup.sh mujoco   (그대로 두기)
# 터미널 2:
ros2 run so101_project joint_command.py --named zero --time 3      # 여유가 가장 큰 자세로 먼저
ros2 run so101_project leader_follow.py --source demo --period 6 --amplitude 0.5
#  준비 없이 쓰려면:  ./scripts/08_run.sh leader_follow.py --source demo ...
```

**왜 `zero` 에서 시작하나.** 데모는 *현재 자세*를 중심으로 흔들고, 진폭은 관절 한계까지 남은
여유에 맞춰 자동으로 줄어든다. `rest` 자세는 `shoulder_lift`가 한계에서 0.175 rad밖에 안
떨어져 있어서 거의 못 움직인다. `zero`(모두 0)는 여유가 가장 커서 크게 흔들 수 있다.

터미널에 0.5초마다 이런 줄이 올라간다(**이 줄을 화면에 같이 넣고 찍으면 설명이 끝난다**):

```
[   27] pan=+0.923  lift=+0.315  elbow=-0.228  wristF=-0.069  wristR=-0.187  grip=+1.275   최대추종오차 0.086 rad (elbow_flex)
```

- 앞의 값들 = **leader가 만든 명령**, `최대추종오차` = 명령과 **MuJoCo 실측**의 차이.
  즉 이 숫자가 "따라오고 있다"의 정량적 증거다.
- 종료는 `Ctrl`+`C`. 마지막 명령 위치에서 멈춘다.
- 시작 자세를 매번 같게 하려면 먼저 `ros2 run so101_project group_goal_client.py --group arm --named rest --execute`.
- `--amplitude`는 **현재 자세에서 관절 한계까지 남은 여유에 맞춰 자동으로 줄어든다**(경고 없이 계속 돈다).
- 추종오차가 커지면(0.2 rad 이상) 요구 속도가 너무 빠른 것이다. `--period`를 늘리거나
  `--amplitude`를 줄인다. 실제로 `--period 5 --amplitude 0.5`에서는 0.38 rad까지 벌어졌고,
  `--period 6~8 --amplitude 0.35`에서는 0.05~0.10 rad에 머문다. **이 값 자체가 물리 시뮬레이션의
  결과물**이라 mock에서는 거의 0이 된다.

**찍을 것**: MuJoCo 팔이 움직이고 → RViz 모델이 같이 움직이고 → 터미널 숫자가 흐르는 한 화면.

### 2-3. 방법 B — 슬라이더를 leader로 (손으로 조작하는 느낌, 사진용)

leader 역할을 슬라이더 창이 대신한다. 블로그의 "leader 암을 손으로 움직인다"에 가장 가까운 조작감이다.

```bash
# 터미널 2: 가상 leader 창 (여기서 슬라이더를 움직인다)
./scripts/05_gui.sh leader

# 터미널 3: leader를 따라가게 만드는 노드
ros2 run so101_project leader_follow.py --source topic
```

- 슬라이더 창은 `/leader/joint_states`로만 발행한다. **로봇을 직접 움직이지 않는다.**
  실제 추종은 `leader_follow.py`가 한다(그래서 창을 닫아도 로봇은 마지막 자리에 그대로 있다).
- `/joint_states`(실측)와 `/leader/joint_states`(leader)를 **일부러 다른 토픽으로 분리**했다.
  같은 토픽을 쓰면 상태와 명령이 섞여 로봇이 발진한다.
- 슬라이더를 확 밀어도 `--max-vel`(기본 2.0 rad/s)로 제한되어 팔이 튀지 않는다.

오늘 확인된 동작(참고): leader가 0으로 있으면 팔은 rest 자세(`lift=-1.50, elbow=+1.50`)에서
0까지 **속도 제한을 받으며 부드럽게** 내려가고, 도착 후 추종오차는 0.002~0.003 rad로 안정된다.

### 2-4. 방법 C — 실물 leader 암 → MuJoCo follower (집에서, 이게 제일 그림이 좋다)

실물 leader는 **읽기만** 하므로 follower를 MuJoCo로 두는 것이 가능하다.
"손으로 만지는 실물 + 화면에서 따라오는 시뮬레이터"는 블로그에 없는 조합이다.

**전제 (한 번만).** 이 노드는 한 프로세스에서 `lerobot`과 `rclpy`를 같이 쓴다. 그래서 가상환경을
`--system-site-packages`로 만들어야 한다(그러지 않으면 `import rclpy`가 실패한다).
현재 24.04 배포판에는 LeRobot이 설치돼 있지 않다 — 집에서 이 한 번만 하면 된다.

```bash
python3 -m venv --system-site-packages ~/venvs/so101-hardware
source ~/venvs/so101-hardware/bin/activate
source /opt/ros/jazzy/setup.bash && source ~/so101_ws/install/setup.bash
source scripts/env.sh
pip install -U pip && pip install 'lerobot[core_scripts,feetech]' evdev
python -c 'import lerobot, rclpy; print("lerobot", lerobot.__version__, "+ rclpy OK")'
```

```bash
# 0) leader 포트 확인 (LeRobot 가상환경에서)
lerobot-find-port

# 1) 반드시 먼저: 발행하지 않고 값만 본다 (부호·단위 확인)
ros2 run so101_project leader_follow.py --source lerobot --port /dev/ttyACM1 \
    --leader-id my_leader --print-only

# 2) 방향이 반대인 관절이 있으면 뒤집는다
ros2 run so101_project leader_follow.py --source lerobot --port /dev/ttyACM1 \
    --leader-id my_leader --flip shoulder_lift,elbow_flex --max-vel 1.0
```

주의할 점만 정리하면:

- **`--print-only`를 먼저 하지 않으면 안 된다.** LeRobot 버전에 따라 값이 도(`--units deg`)이거나
  정규화값(`--units norm`, -100~100)이라 부호·범위를 눈으로 확인해야 한다.
- leader의 캘리브레이션(`lerobot-calibrate`)이 끝나 있어야 값이 의미를 갖는다.
- **같은 USB 포트를 두 프로그램이 열 수 없다.** leader와 follower가 각각 다른 포트여야 한다.
  실물 follower까지 쓸 거면 2-5로 간다.

### 2-5. 방법 D — 블로그 원본 그대로: 실물 leader → 실물 follower

이건 LeRobot 자체 기능이고 ROS를 거치지 않는다(블로그도 그렇다).

```bash
source ~/venvs/so101-hardware/bin/activate
lerobot-teleoperate --help      # 설치된 버전의 정확한 플래그를 먼저 확인
```

**ROS 드라이버(`06_bringup.sh real`)와 동시에 실행할 수 없다.** 둘 다 follower의 USB를 열려고 한다.
텔레옵을 끝내고 프로그램을 종료한 다음 ROS를 띄운다. RViz로 실물 자세를 보려면
`./scripts/06_bringup.sh real launch_moveit:=false`로 상태만 읽는 모드가 있다(문서 02 3절).

## 3. 미션 2 — 명령으로 제어 (블로그 10편)

블로그 10편은 "토픽으로 목표 각도를 보내 서보를 움직이는 역방향 경로"였다.
우리는 같은 일을 **시간 궤적**으로 보낸다(MoveIt 결과를 그대로 실행하려면 이 형식이어야 한다).
**MoveIt은 관여하지 않는다. 충돌 검사도 없다.**

### 3-1. 기본 — 도(deg)로 지정하고 결과·오차까지 받기

```bash
# 터미널 2 (터미널 1은 bringup 유지)
ros2 run so101_project joint_command.py --deg shoulder_pan=30,elbow_flex=-20 --time 2.5
```

오늘 MuJoCo 백엔드에서 실제로 나온 출력 (값은 `shoulder_pan=25`로 실행한 것):

```
[INFO] arm_controller <- shoulder_pan=+0.4363rad(+25.0deg)  (2.5s)
[INFO] arm_controller 실행 완료: SUCCESSFUL

  관절            목표(rad)    실측(rad)     오차(rad)
  elbow_flex     +1.5709     +1.5713     +0.0004
  shoulder_lift  -1.5699     -1.5699     +0.0000
  shoulder_pan   +0.4363     +0.4363     +0.0000
  ...
  최대 오차 0.0004 rad (0.03 deg)
```

- 지정하지 않은 관절은 **현재 위치를 유지**한다(다른 관절이 갑자기 0으로 가지 않는다).
- `--time`은 목표까지 걸릴 시간. 짧게 주면 빠르고 거칠게, 길게 주면 천천히 움직인다.
- 마지막 표가 **"명령했다"가 아니라 "그 자리에 실제로 갔다"의 증거**다. 촬영 포인트.

### 3-2. 블로그와 같은 "토픽으로 던지기" + 원시 명령 보기

```bash
ros2 run so101_project joint_command.py --deg shoulder_pan=0 --time 2 --via topic --show-raw
```

`--show-raw`는 **같은 일을 하는 순수 CLI 명령**을 출력한다. 블로그의 `ros2 topic pub` 방식과
우리 방식이 같은 것임을 한눈에 보여주므로, 설명용 캡쳐로 좋다:

```
ros2 topic pub --once /arm_controller/joint_trajectory trajectory_msgs/msg/JointTrajectory \
 '{joint_names: [shoulder_pan, shoulder_lift, elbow_flex, wrist_flex, wrist_roll],
   points: [{positions: [0.5236, 0.0, -0.3491, 0.0, 0.0], time_from_start: {sec: 2}}]}'
```

| 방식 | 결과를 받나 | 언제 쓰나 |
|---|---|---|
| `--via action` (기본) | 받는다 (성공/실패/오차) | 검증·시연·자동화 |
| `--via topic` | 못 받는다 (던지고 끝) | 블로그와 같은 경로임을 보여줄 때 |

### 3-3. 안전 시연 — 한계를 넘는 명령은 거부된다 (좋은 촬영거리)

```bash
ros2 run so101_project joint_command.py --deg shoulder_pan=200 --time 2
# [ERROR] shoulder_pan=+3.4907 rad 는 한계 [-1.9199, +1.9199] 를 벗어난다. 값을 고치거나 --clamp 를 쓴다
# exit 2
```

이 한계는 코드에 박아 넣은 값이 아니라 **실행 중인 로봇의 `/robot_description`에서 읽은 값**이다.
모델을 바꾸면 검증 기준도 따라 바뀐다.

### 3-4. 상대 이동·그리퍼

```bash
ros2 run so101_project joint_command.py --deg shoulder_pan=+15 --relative   # 현재에서 15도 더
ros2 run so101_project joint_command.py --rad gripper=1.5 --time 1.0        # 그리퍼 열기
ros2 run so101_project joint_command.py --rad gripper=-0.16 --time 1.0      # 닫기
```

그리퍼는 `gripper_controller`로 자동 분기된다(팔과 그리퍼는 서로 다른 컨트롤러다).

### 3-5. 슬라이더로 직접 구동 (0-2에서 rqt를 설치한 경우)

```bash
./scripts/05_gui.sh sliders
```

창에서 ① controller manager `/controller_manager` → ② controller `arm_controller` →
③ 왼쪽 빨간 전원 아이콘 클릭 → 슬라이더 활성화. 이것도 미션 2의 경로(직접 명령)다.
**미션 1의 leader 창(`05_gui.sh leader`)과 동시에 쓰지 않는다.** 두 곳에서 같은 컨트롤러에
명령하면 서로를 덮어쓴다.

### 종료 코드 (자동화·문서화용)

| 코드 | 뜻 |
|---|---|
| 0 | 성공 |
| 2 | 입력 오류 또는 관절 한계 초과 |
| 3 | 목표 거부 / 컨트롤러 없음 |
| 4 | 시간초과 |
| 5 | 실행 실패 (경로·목표 허용오차 위반 등) |
| 6 | `/robot_description` 또는 `/joint_states`를 받지 못함 (= bringup이 없거나 통신 막힘) |

## 4. 미션 3 — MoveIt으로 제어 (블로그 13편)

블로그 13편은 Setup Assistant로 `arm`/`gripper` 그룹을 만들고 **ZMQ 브리지**로 실행했다.
우리는 그룹 설정을 그대로 재사용하고 실행만 **표준 JTC**로 바꿨다(문서 01의 D4).
그래서 같은 계획이 mock·MuJoCo·실물에서 그대로 실행된다.

미션 2와의 차이가 곧 MoveIt을 쓰는 이유다:

| | 미션 2 (직접 명령) | 미션 3 (MoveIt) |
|---|---|---|
| 충돌 검사 | 없음 | **있음** (자기충돌 행렬 + 씬) |
| 관절 한계·속도 | 우리가 검증 | MoveIt이 계획 단계에서 보장 |
| 경로 | 직선 보간 | 계획기(OMPL)가 만든 경로 |
| 실패 | 실행해 보고 알게 됨 | **계획 단계에서 미리 알 수 있음** |
| 목표 지정 | 관절 각도 | 관절 각도 + 저장 자세 + (5축이라 제한적인) 위치 |

### 4-1. RViz에서 직접 조작하기 (마우스로 계획하고 실행까지)

**버튼은 RViz에만 있다. MuJoCo 창에는 로봇에 명령하는 버튼이 없다.**
MuJoCo 창은 물리 뷰어라서 시점 회전·렌더링 옵션만 있고, 로봇 명령은 전부 ROS로 들어간다.
"Execute를 누른다"는 말은 **RViz의 MotionPlanning 패널에 있는 Execute 버튼**을 뜻한다.
(명령줄의 `--execute` 옵션이 정확히 그 버튼과 같은 일을 한다)

#### 화면 구조

`06_bringup.sh mujoco`로 띄우면 RViz가 MoveIt 설정과 함께 열린다
(설정 파일에 `Planning Group: arm`, `Query Goal State: true`가 이미 들어 있다).

| 위치 | 내용 |
|---|---|
| 왼쪽 위 **Displays** | 표시 항목 트리. `MotionPlanning`이 여기 있다 |
| 왼쪽 아래 **MotionPlanning 패널** | **조작판.** 탭: Context / Planning / Manipulation / Scene Objects / Stored Scenes / Stored States / Status / **Joints** |
| 가운데 3D 화면 | 흰색·회색 = 현재 로봇(`/joint_states`), **주황색 = 목표 자세**, 반투명 = 계획된 경로 재생 |

패널이 안 보이면 Displays 트리에서 `MotionPlanning` 체크가 켜져 있는지 본다(패널은 이 항목이 만든다).

#### 순서

1. **그룹 선택** — Planning 탭 위쪽 **Planning Group**을 `arm`으로 둔다(그리퍼만 움직이려면 `gripper`).
2. **목표 자세 정하기** — 세 가지 방법이 있다.
   - **(A) 저장 자세** — Planning 탭의 **Goal State** 드롭다운에서 `rest` / `extended` / `zero`를
     고르고 옆의 **Update** 버튼을 누른다. 주황색 팔이 그 자세로 바뀐다. *가장 쉽다.*
     (`gripper` 그룹에서는 `open` / `closed`)
   - **(B) 관절 슬라이더** — **Joints 탭**에서 관절별 슬라이더를 움직이면 주황색 목표가 실시간으로
     따라온다. **5축 로봇에서는 이게 정석이다.**
   - **(C) 끝점 마커 드래그** — 3D 화면에서 주황색 팔 끝의 화살표·링을 마우스로 끈다.
     SO-101은 5축이라 임의의 위치·방향을 만들 수 없어서 **IK가 자주 실패한다**(마커가 안 따라오거나
     링크가 빨갛게 된다). 우리 설정 문제가 아니라 자유도 문제다.
3. **계획** — Planning 탭 Commands의 **Plan**. 성공하면 반투명 로봇이 시작→목표 경로를 반복 재생한다.
   **이 단계에서는 MuJoCo의 팔은 움직이지 않는다.** (계획은 아직 실행이 아니다)
4. **실행** — **Execute**. 이때 MuJoCo의 팔이 그 경로대로 움직이고, 흰색 현재 로봇도 따라온다.
   `Plan & Execute`는 3·4를 한 번에 한다.
5. **결과 확인** — 패널의 상태 표시(또는 Status 탭)에 성공/실패가 뜬다. 실패하면 이유가 나온다
   (`START_STATE_IN_COLLISION`이면 4-3으로).

#### 눈으로 보이는 신호

- **충돌하는 링크는 빨갛게 표시된다.** 4-3의 자기충돌 문제를 화면에서 바로 확인할 수 있다.
- 목표가 불가능하면 Plan이 실패하고 반투명 재생이 아예 없다.
- 목표와 현재가 같으면 Plan은 성공하지만 볼 게 없다(움직일 거리가 0이다).

#### 어디에 무엇이 있나 · 명령줄과의 대응

| 하고 싶은 것 | RViz | 명령줄 |
|---|---|---|
| 그룹 바꾸기 | Planning 탭 → Planning Group | `--group arm` / `--group gripper` |
| 저장 자세를 목표로 | Goal State 드롭다운 → Update | `--named rest` |
| 관절별 목표 | **Joints 탭** 슬라이더 | `--joints shoulder_pan=0.4,elbow_flex=-0.3` |
| 계획만 하기 | **Plan** | (`--execute`를 빼면 계획만) |
| 실제로 움직이기 | **Execute** | `--execute` |
| 천천히 움직이기 | Planning 탭 Options의 Velocity/Accel Scaling | `--vel 0.1 --acc 0.1` |
| 시작 자세를 현재로 맞추기 | Start State → `<current>` → Update | 자동 (항상 실측 상태에서 시작한다) |

**찍을 것**: Plan을 눌러 반투명 경로가 재생되는 순간(계획) → Execute 후 MuJoCo가 따라가는 순간(실행).
"계획과 실행이 분리돼 있다"가 MoveIt의 핵심이고, 그 두 장이 그걸 보여준다.

> MuJoCo 창에서는 마우스로 시점만 바꾼다(드래그 회전, 휠 줌). 창의 키보드 단축키는
> 시뮬레이션 자체를 일시정지시킬 수 있어서, 촬영 중에 눌렀다가 "로봇이 명령에 반응하지 않는다"로
> 보일 수 있다.

### 4-2. 명령줄에서 (블로그 14편의 "외부 프로그램" 자리)

#### 이 명령이 정확히 무슨 뜻인가

```
ros2 run so101_project group_goal_client.py --group arm --named rest --execute
└──── ①────┘ └──② ────┘ └───────③───────┘ └───④───┘ └────⑤────┘ └───⑥───┘
```

| | 뜻 |
|---|---|
| ① `ros2 run` | 설치된 패키지의 실행 파일을 실행한다 |
| ② `so101_project` | 우리 패키지 |
| ③ `group_goal_client.py` | MoveIt에 목표를 보내는 우리 노드 (RViz의 조작판을 명령줄로 대신한다) |
| ④ `--group arm` | **Planning Group** = 함께 계획할 관절 묶음. `arm`은 5관절, `gripper`는 1관절 |
| ⑤ `--named rest` | SRDF에 저장된 자세 이름. arm: `zero`/`rest`/`extended`, gripper: `open`/`closed` |
| ⑥ `--execute` | **실제로 움직인다.** 빼면 계획만 하고 아무것도 움직이지 않는다 |

한 줄로: **"MoveIt아, `arm` 그룹을 지금 자세에서 `rest` 자세까지 충돌 없이 갈 수 있는 경로를
계획하고, 그 경로를 컨트롤러에 실행시켜라."**

#### `planned_points=0`이면 화면은 가만히 있는 게 정상이다

```
error_code=SUCCESS(1)  planned_points=0  planning_time=0.000s
궤적 점이 0개다: 이미 목표 자세에 있어서 움직일 것이 없다 (정상)
worst error 0.0004 rad on elbow_flex
```

`planned_points`는 MoveIt이 만든 경로점 개수다. **0이면 시작 자세가 이미 목표 자세**여서
실행할 궤적이 없다는 뜻이다(오차 0.0004 rad = 이미 도착해 있음). 실패가 아니다.
움직이는 것을 보려면 **다른 자세**를 목표로 준다:

```bash
ros2 run so101_project group_goal_client.py --group arm --named extended --execute --vel 0.2
ros2 run so101_project group_goal_client.py --group arm --named rest --execute --vel 0.2
```

이러면 `planned_points=39`처럼 나오고 두 창이 실제로 움직인다(오늘 확인한 값이다).

```bash
# 계획만 (기본값. 아무것도 움직이지 않는다)
ros2 run so101_project group_goal_client.py --group arm --named rest

# 계획 + 실행
ros2 run so101_project group_goal_client.py --group arm --named rest --execute --vel 0.2

# 관절 목표를 직접
ros2 run so101_project group_goal_client.py --group arm \
    --joints shoulder_pan=0.4,elbow_flex=-0.3 --execute --vel 0.15

# 그리퍼 그룹
ros2 run so101_project group_goal_client.py --group gripper --named open --execute
```

오늘 MuJoCo에서 실제로 나온 실행 결과:

```
error_code=SUCCESS(1)  planned_points=15  planning_time=0.000s
joint         target     actual     error
elbow_flex     +1.5700   +1.5756    0.0056
shoulder_pan   +0.0000   -0.0061    0.0061
wrist_roll     +0.0000   -0.0092    0.0092
worst error 0.0092 rad on wrist_roll
```

오차가 0이 아닌 것이 **정상**이다. 미션 2의 mock에서는 오차가 정확히 0이었지만
MuJoCo에서는 중력·관절 마찰·PD 게인 때문에 0.01 rad(0.5도) 수준이 남는다.
**이 차이를 보기 위해 물리 시뮬레이터를 쓴다.**

### 4-3. `START_STATE_IN_COLLISION(-10)`이 나오면 — 실패가 아니라 정상 동작이다

```
error_code=START_STATE_IN_COLLISION(-10)  planned_points=0
원인: 지금 자세가 이미 자기충돌 상태다 (설정 문제가 아니다)
  닿은 링크: shoulder_link <-> lower_arm_link  깊이=0.417 mm
  현재 자세: elbow_flex=+1.600, shoulder_lift=-1.700, wrist_flex=+1.140, ...
  빠져나오는 방법 ...
```

**이것이 미션 1·2와 미션 3의 차이가 드러나는 지점이다.** 미션 1·2는 컨트롤러에 직접 명령하므로
충돌 검사를 거치지 않는다. 그래서 URDF 관절 한계 안이어도 팔이 자기 몸에 접힌 자세로 멈출 수
있다. MoveIt은 그 자세에서 계획을 시작할 수 없다(시작점이 이미 불법이면 경로의 의미가 없다).
**MoveIt이 고장난 게 아니라, 미션 1·2가 만들어 둔 자세를 MoveIt이 거부한 것이다.**

복구는 **충돌 검사를 하지 않는 경로로 먼저 빠져나오는 것**이다(그래서 그 경로가 필요하다):

```bash
ros2 run so101_project joint_command.py --named rest --time 3     # 탈출
ros2 run so101_project group_goal_client.py --group arm --named rest --execute   # 다시 계획
```

`joint_command.py --named`는 SRDF 저장 자세(`zero`, `rest`, `extended`, `open`, `closed`)를
읽어서 그 자세로 직접 간다. 갇혔을 때의 탈출구이자, 미션 사이의 초기화 명령이다.

**예방**: 미션 1의 데모는 `--limit-margin`(기본 0.15 rad)만큼 한계에서 떨어져 흔들도록 고쳐
두었다. 그래도 슬라이더나 실물 leader로 직접 접으면 같은 상태가 될 수 있다.
**미션 3을 시작하기 전에 `--named rest` 또는 `--named zero`로 한 번 초기화하는 것을 습관으로
두면 된다.**

> 참고: MuJoCo는 이 자세를 허용한다. MuJoCo의 충돌 형상과 MoveIt(URDF collision + SRDF
> self-collision 행렬)이 보는 형상이 다르기 때문이다. 물리적으로 살짝 스치는 정도(0.4 mm)라도
> MoveIt은 불법으로 본다. 실물에서는 MoveIt 쪽이 옳다 — 서보가 서로를 밀게 된다.

### 4-4. "그룹"을 실제로 이해하는 시연

```bash
# arm 그룹에 그리퍼 관절을 넣으면 거부된다
ros2 run so101_project group_goal_client.py --group gripper --joints shoulder_pan=0.1
# [ERROR] shoulder_pan: not in group 'gripper' (['gripper'])   → exit 2
```

그룹은 "함께 계획되는 관절의 묶음"이다. `arm`은 5축, `gripper`는 1축이고, 우리 SRDF에는
`zero/rest/extended`(arm)와 `open/closed`(gripper) 저장 자세가 들어 있다.
그룹 목록·저장 자세는 코드에 없고 **실행 중인 `/robot_description_semantic`에서 읽는다.**

## 8. 집에서 실물을 붙일 때 (LeRobot + ROS)

정본은 `02_실행내역_및_집에서_할일.md` 3절이다. 여기서는 미션과의 연결만 정리한다.

### 8-1. 순서 (이 순서를 지키는 것이 중요하다)

```bash
# 1) Windows PowerShell (관리자): USB를 WSL로 넘긴다
usbipd list
usbipd attach --wsl --busid <BUSID>          # follower, leader 각각

# 2) WSL: 포트 확인
ls -l /dev/ttyACM*
lerobot-find-port                            # LeRobot 가상환경에서

# 3) LeRobot 캘리브레이션이 끝나 있는지 확인 (이미 되어 있으면 다시 하지 않는다)
#    ROS로 명령하기 전에 반드시 선행되어야 한다 (EEPROM에 기록되는 값이다)

# 4) LeRobot 텔레옵으로 하드웨어 자체를 먼저 확인 (ROS 없이)
lerobot-teleoperate --help                   # 설치 버전의 정확한 플래그 확인 후 사용

# 5) 텔레옵 프로그램을 완전히 종료한다 (같은 USB를 두 프로그램이 열 수 없다)

# 6) ROS로 상태만 읽기 (MoveIt 없이, 안전)
./scripts/06_bringup.sh real usb_port:=/dev/ttyACM0 launch_moveit:=false
#    RViz 모델이 실제 팔 자세와 같은지 본다. 방향이 반대인 관절이 있으면
#    config/joint_mapping.yaml 의 sign/offset_rad 를 확정한다.

# 7) 미션 2를 실물에서 (아주 작은 각도부터)
ros2 run so101_project joint_command.py --deg shoulder_pan=5 --time 3

# 8) 미션 3을 실물에서 (저속)
./scripts/06_bringup.sh real usb_port:=/dev/ttyACM0
ros2 run so101_project group_goal_client.py --group gripper --named open --execute --vel 0.05
ros2 run so101_project group_goal_client.py --group arm --named rest --execute --vel 0.05 --acc 0.05

# 9) 미션 1을 실물 leader로 (follower는 MuJoCo 또는 실물)
ros2 run so101_project leader_follow.py --source lerobot --port /dev/ttyACM1 --print-only
ros2 run so101_project leader_follow.py --source lerobot --port /dev/ttyACM1 --max-vel 1.0
```

### 8-2. 반드시 지킬 것

| 규칙 | 이유 |
|---|---|
| **LeRobot 텔레옵과 `06_bringup.sh real`을 동시에 켜지 않는다** | 같은 시리얼 포트를 두 프로그램이 열 수 없다 |
| **`--print-only`로 값을 먼저 본다** | LeRobot 버전에 따라 단위가 도/정규화값이라 부호·범위 확인이 먼저다 |
| **처음엔 `--vel 0.05`, 작은 각도** | 실물은 되돌릴 수 없다. 시뮬레이터와 달리 부딪히면 부러진다 |
| **`sign`/`offset_rad`을 `joint_mapping.yaml`에 기록** | 다음에 다시 찾지 않기 위해서다. 이 파일이 모델↔모터 계약서다 |
| **캘리브레이션을 다시 돌리지 않는다** | 이미 텔레옵을 해 본 장비면 EEPROM 값이 맞춰져 있다. `setup-motors`를 다시 돌리면 그 값이 바뀐다 |

### 8-3. 실물에서 달라지는 것 (미션별)

| 미션 | 시뮬레이터 | 실물 |
|---|---|---|
| 1 (추종) | 오차 0.003~0.10 rad | 서보 응답·부하로 더 커진다. `--max-vel`을 낮춰 시작 |
| 2 (직접 명령) | 오차 0.0004 rad | `sign`/`offset` 확정 전에는 방향이 반대일 수 있다 |
| 3 (MoveIt) | 오차 0.0092 rad | 충돌 검사는 여전히 자기충돌만 본다. **책상·물체는 모델에 없다** |
