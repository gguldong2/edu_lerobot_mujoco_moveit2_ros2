# 시나리오별 실행법

"MuJoCo에서 MoveIt 2로 그룹 제어하고, 필요하면 텔레옵도 한다"를 실제로 하는 방법.
개념·스크립트 설명은 [03_사용법.md](03_사용법.md), 실물 절차는 [02_실행내역_및_집에서_할일.md](02_실행내역_및_집에서_할일.md).

> 이 문서의 명령은 **저장소 루트에서** 실행한다. 미션 단위(블로그 9·10·13편)의 절차와
> 녹화 방법은 **[05_미션_가이드.md](05_미션_가이드.md)** 가 정본이다.

## 0. 먼저 개념: "연결"과 "계획"은 서로 다른 축이다

블로그를 읽을 때도, 우리 프로젝트를 쓸 때도 이 두 축을 분리해서 보면 전부 명확해진다.

```
                    ┌──────────── 계획 축 (목표를 어떻게 만드나) ────────────┐
                    │  MoveIt 없이                    MoveIt 2로            │
   ┌────────────────┼──────────────────────────────┼───────────────────────┤
연 │ mock           │ 슬라이더로 값만 바꿔보기      │ 배선 검증 (지금 1단계) │
결 │ MuJoCo         │ 슬라이더로 물리 확인          │ ★ 이번 목표            │
축 │ 실물 SO-101    │ LeRobot 텔레옵 (기존 경험)    │ 집에서 최종 목표       │
   └────────────────┴──────────────────────────────┴───────────────────────┘
```

- **연결 축** = 명령을 어디에 쓰나. USB·모터·캘리브레이션·`hardware_type`의 문제.
- **계획 축** = 목표를 어떻게 만드나. 그룹·충돌 회피·궤적·`/move_action`의 문제.

**두 축은 독립이다.** 그래서 실물 없이도 계획 축을 완성할 수 있고(지금 하는 일),
실물이 와도 계획 축은 손대지 않고 연결 축만 `hardware_type:=real`로 갈아끼운다.

### MoveIt이 있을 때와 없을 때의 실제 차이

| | MoveIt 없이 (텔레옵·슬라이더·LeRobot) | MoveIt 2로 |
|---|---|---|
| 입력 | 관절 각도 그 자체(리더팔 자세, 슬라이더 값, 정책 출력) | 목표(그룹 + 관절값 또는 자세) |
| 중간 처리 | 없음. 현재 값에서 목표 값으로 바로 | 충돌 회피·관절 한계를 지키는 **경로**를 만들고 시간 궤적으로 변환 |
| 안전 | 자기충돌·테이블 충돌을 모른다 | 계획 단계에서 걸러진다 |
| 그룹 개념 | 없음 | `arm` / `gripper` 단위로 계획 |
| 실패했을 때 | 그냥 움직인다 | "계획 실패"로 거부한다 |
| 잘 맞는 용도 | 데이터 수집, 직접 조작, 학습된 정책 실행 | 목표 지향 동작, 장애물 회피, 재현 가능한 검증 |

둘은 배타적이지 않다. **같은 컨트롤러(`arm_controller`)를 공유하지만 동시에 쓰지는 않는다.**
한쪽이 궤적을 실행하는 중에 다른 쪽이 명령을 보내면 로봇이 두 자세 사이를 오간다.

### 블로그에서도 이 두 축이 나뉘어 있다

| 블로그 | 어느 축 | 내용 |
|---|---|---|
| (5)(6) 부품·조립·모터 | 연결 | 하드웨어 자체 |
| (8) robot_status_publisher | 연결 | 실물 각도를 읽어 ROS로 올리기 (MoveIt 없음) |
| (9) 실물 + RViz 동기화 | 연결 | 읽은 값을 화면에 반영 (RViz는 표시만) |
| (10) Joint Command 역방향 | 연결 | ROS에서 각도를 써서 서보를 돌리기 (**여기까지 MoveIt 없음**) |
| **(13) MoveIt 통합** | 계획 | 그룹·계획을 얹고, 계획 결과를 (10)에서 만든 경로로 흘려보냄 |
| **(14) Unreal → MoveIt → 실물** | 계획 + 연결 | 두 축이 합쳐진 end-to-end |

즉 블로그는 **연결을 먼저 완성하고 그 위에 MoveIt을 얹은** 순서다.
우리는 실물이 없으니 **순서를 뒤집어 계획 축을 시뮬레이터로 먼저 완성**하고, 마지막에 연결만 바꾼다.
그 갈아끼우는 지점이 `hardware_type` 인자 하나다.

## 1. bringup이 무슨 뜻인가 · 터미널을 왜 2개 쓰나

**bringup = 로봇을 "실행 상태로 올리는" launch.** 노드(모델 발행·컨트롤러 매니저·MoveIt·RViz)를
한꺼번에 띄우고, **그 터미널을 계속 점유한 채 로봇이 켜져 있는 동안 돌아간다.** Ctrl+C로 내리면 로봇이 내려간다.

그래서 터미널이 최소 2개 필요하다.

| 터미널 | 역할 | 특징 |
|---|---|---|
| **터미널 1** | bringup (`06_bringup.sh`) | 계속 점유. 로그가 흐른다. 여기에 다른 명령을 치지 않는다 |
| **터미널 2** | 점검·제어 (`04`, `05`, `group_goal_client`) | 명령을 실행하고 끝난다 |

스크립트 번호와 대응하면:

| 스크립트 | 성격 |
|---|---|
| `00` 설치, `01` 빌드 | **준비.** 한 번만. 로봇은 아직 안 돈다 |
| `02` URDF 점검, `03` MJCF 점검 | **점검.** 파일만 본다. 로봇은 안 돈다 |
| **`06_bringup.sh`** | **실행. 여기서 처음으로 로봇/시뮬레이터가 돈다** |
| `04` 스모크 테스트, `05` GUI | bringup이 돌고 있는 상태에서 쓰는 도구 |

> 흔한 실수: 문서의 두 터미널용 명령을 한 터미널에 통째로 붙여넣는 것.
> `ros2 launch ...` 줄이 먼저 실행되며 그 터미널을 점유해야 하는데, 붙여넣기하면
> 뒤 줄이 같은 터미널에서 실행돼 엉킨다. **아래 시나리오는 터미널별로 블록을 나눠 두었다.**

## 2. 시나리오 A — mock에서 MoveIt 그룹 제어 (제일 먼저)

물리 없이 "목표 → 계획 → 실행 → 상태" 배선만 확인한다. 실패 지점이 가장 적어 문제를 빨리 찾는다.

**터미널 1**

```bash
cd <저장소 루트>          # 예: cd ~/edu_lerobot_mujoco_moveit2_ros2
./scripts/06_bringup.sh mock
```

RViz 창이 뜨고 로그가 흐르면 성공. 이 터미널은 그대로 둔다.

**터미널 2**

```bash
cd <저장소 루트>          # 예: cd ~/edu_lerobot_mujoco_moveit2_ros2
./scripts/04_smoke_test.sh
```

성공 신호: `arm_controller`·`gripper_controller`·`joint_state_broadcaster`가 `active`,
plan-only 두 건 `SUCCESS`, 잘못된 요청은 거부.

**RViz에서 직접 해보기** (터미널 1이 띄운 창)

1. 왼쪽 아래 `MotionPlanning` 패널 → `Planning` 탭
2. `Planning Group`을 `arm`으로
3. `Goal State`를 `rest` 또는 `extended` 선택 (또는 오렌지색 마커를 드래그)
4. `Plan` → 계획 경로 애니메이션 확인 → `Execute`
5. `Planning Group`을 `gripper`로 바꾸고 `open` / `closed`로 반복

## 3. 시나리오 B — MuJoCo 물리에서 같은 제어 (이번 핵심 목표)

**터미널 1**

```bash
./scripts/06_bringup.sh mujoco
```

MuJoCo 창(물리)과 RViz 창(계획·상태)이 함께 뜬다. 팔은 MJCF의 `rest` keyframe 자세에서 시작한다.

**터미널 2**

```bash
./scripts/04_smoke_test.sh          # 이번에는 /clock 이 나오고 use_sim_time=true 여야 한다
```

```bash
ros2 run so101_project group_goal_client.py --group arm --named extended --execute --vel 0.1
```

성공 신호: MuJoCo 창의 팔이 실제로 움직이고, 클라이언트가 마지막에 출력하는
`joint target actual error` 표의 오차가 허용치 안.

**mock과 다른 점** — 여기서부터 물리가 개입한다.

- 중력 때문에 목표와 실측이 완전히 같지 않다(추종 오차). 오차가 크면 MJCF actuator `kp`를 조정한다.
- 실행 속도를 올리면 오차가 커진다. `--vel 0.1`부터 시작한다.
- `mujoco_keyframe:=""`로 띄우면 0 자세에서 시작한다.

## 4. 시나리오 C — "그룹"을 실제로 이해하기

그룹은 **함께 계획할 관절 묶음**이다(네트워크 그룹이 아니다). 다음을 차례로 해보면 개념이 잡힌다.

```bash
# 1) arm 그룹은 팔 5관절만 건드린다. 그리퍼는 그대로 있어야 한다
ros2 run so101_project group_goal_client.py --group arm --named rest --execute --vel 0.1

# 2) gripper 그룹은 그리퍼 1관절만 움직인다. 팔은 그대로여야 한다
ros2 run so101_project group_goal_client.py --group gripper --named closed --execute

# 3) 그룹에 없는 관절을 넣으면 로봇에 명령이 가기 전에 거부된다
ros2 run so101_project group_goal_client.py --group gripper --joints shoulder_pan=0.1

# 4) 관절 한계를 넘기면 역시 거부된다 (shoulder_pan 한계는 ±1.91986)
ros2 run so101_project group_goal_client.py --group arm --joints shoulder_pan=3.0

# 5) 직접 값 지정 (rad). 계획만 먼저 → 괜찮으면 --execute
ros2 run so101_project group_goal_client.py --group arm --joints shoulder_pan=0.4,elbow_flex=-0.5
ros2 run so101_project group_goal_client.py --group arm --joints shoulder_pan=0.4,elbow_flex=-0.5 --execute --vel 0.1
```

클라이언트가 그룹 구성을 어디서 아는지: **SRDF에서 읽는다**(`arm`은 `base_link`→`gripper_frame_link`
체인이라 팔 5관절이 자동 포함, `gripper`는 관절 1개). 한계는 URDF에서 읽는다. 하드코딩이 없다.

## 5. 시나리오 D — 텔레옵 (MoveIt 없이 직접 제어)

네 가지 방법이 있고, 목적이 다르다. **미션 형태의 상세 절차와 녹화 방법은 `05_미션_가이드.md`에 있다.**

### D-0. `leader_follow.py` — 블로그 9편의 leader→follower 추종 (권장 출발점)

```bash
# 터미널 1: ./scripts/06_bringup.sh mujoco
# 터미널 2:  (08_run.sh 는 ROS 환경 준비까지 알아서 한다)
./scripts/08_run.sh leader_follow.py --source demo     # 하드웨어 없이 (데모 신호)
./scripts/05_gui.sh leader                             # 또는 슬라이더를 leader 로 (터미널 2)
./scripts/08_run.sh leader_follow.py --source topic    # 그 슬라이더를 따라가게 (터미널 3)
```

URDF 한계 clamp와 `--max-vel` 속도 제한이 항상 걸리고, 0.5초마다 **최대 추종오차**를 출력한다.
실물 leader는 `--source lerobot --port ... --print-only`로 부호·단위를 먼저 확인한 뒤 쓴다.

### D-1. rqt 슬라이더 (설치만 하면 지금 바로 가능)

**터미널 1**: `./scripts/06_bringup.sh mujoco`
**터미널 2**:

```bash
sudo apt install -y ros-jazzy-rqt-joint-trajectory-controller   # 처음 한 번
./scripts/05_gui.sh sliders
```

창에서 ① controller manager `/controller_manager` → ② controller `arm_controller` →
③ 왼쪽 전원 아이콘 클릭 → 슬라이더 활성화. 움직이면 MuJoCo 팔이 따라온다.
**MoveIt을 거치지 않으므로 충돌 검사가 없다.** 조작감 확인·촬영용.

### D-2. LeRobot 키보드 텔레옵 (시뮬레이터 대상, 어댑터 설치 필요)

`ycheng517/lerobot-ros` 어댑터를 우리 컨트롤러에 맞춰 쓰는 방식. 설치·설정은
`02_실행내역_및_집에서_할일.md`의 "LeRobot 어댑터" 절에 정리돼 있다. 요점만:

```bash
python3 -m venv --system-site-packages ~/venvs/so101-lerobot-ros
source ~/venvs/so101-lerobot-ros/bin/activate
source /opt/ros/jazzy/setup.bash && source ~/so101_ws/install/setup.bash
git clone https://github.com/ycheng517/lerobot-ros ~/so101_ws/vendor/lerobot-ros
pip install -e ~/so101_ws/vendor/lerobot-ros/lerobot_robot_ros \
            -e ~/so101_ws/vendor/lerobot-ros/lerobot_teleoperator_devices
```

그 다음 어댑터 config를 `ActionType.JOINT_TRAJECTORY`,
`/arm_controller/joint_trajectory`, `/gripper_controller/joint_trajectory`, `/joint_states`,
관절명 5+1로 맞추고:

```bash
lerobot-teleoperate --robot.type=so101_ros --robot.id=so101_sim \
  --teleop.type=keyboard_joint --teleop.id=keyboard_sim --display_data=false
```

**Gazebo launch는 실행하지 않는다**(어댑터 예제가 Gazebo 기준일 뿐, 우리는 MuJoCo를 쓴다).

### D-3. 실물 leader-follower 텔레옵 (집에서, 기존 방식)

블로그에는 이 편이 없다(15편은 Record/Replay). **원래 LeRobot 기능**이므로 기존에 하던 방식을 쓴다.
ROS 드라이버와 **같은 USB 포트를 동시에 열 수 없으므로** 텔레옵을 끝내고 프로그램을 종료한 뒤 ROS를 띄운다.

```bash
source ~/venvs/so101-hardware/bin/activate
lerobot-teleoperate --help      # 설치 버전의 정확한 플래그 확인 후 사용
```

## 6. 시나리오 E — 실물 (집에서)

순서와 안전 절차는 `02_실행내역_및_집에서_할일.md` 3절이 정본이다. 요약만:

```bash
# 0) LeRobot 캘리브레이션이 끝나 있어야 한다 (EEPROM 기록)
# 1) 상태만 읽어 RViz와 대조 (MoveIt 없이)
./scripts/06_bringup.sh real usb_port:=/dev/ttyACM0 launch_moveit:=false

# 2) joint_mapping.yaml 의 sign/offset 확정 후, 계획까지 포함해 저속 실행
./scripts/06_bringup.sh real usb_port:=/dev/ttyACM0
ros2 run so101_project group_goal_client.py --group gripper --named open --execute --vel 0.05
ros2 run so101_project group_goal_client.py --group arm --named rest --execute --vel 0.05 --acc 0.05
```

시뮬레이션에서 쓰던 명령이 **글자 하나 안 바뀌고 그대로 실물에 적용된다.** 그게 이 설계의 목적이다.

## 부록: 통신이 막혔을 때 (WSL 특유의 문제)

증상: bringup 로그에는 컨트롤러가 활성화됐다고 나오는데 **다른 터미널에서 `ros2 node list`가 비어 있다**,
`ros2 control list_controllers`가 멈추거나 `TimeoutError: [Errno 110]` traceback,
`spawner`가 `Could not contact service /controller_manager/list_controllers`,
controller_manager가 `Waiting for data on 'robot_description' topic`을 계속 반복.

원인은 ROS 코드가 아니라 **WSL의 프로세스 간 DDS 통신/시계**다.

**가장 먼저 이것을 실행한다. 아래 절차를 자동으로 수행하고 어느 설정에서 통신이 되는지 알려준다.**

```bash
./scripts/07_doctor.sh          # 진단만
./scripts/07_doctor.sh --fix    # 복구 (실행 중인 ROS 를 모두 내린다)
```

### 이 랩탑에서 확인된 근본 원인 (2026-09-09, 측정으로 확정)

**원인은 `networkingMode=mirrored`이고, 127.0.0.1 통신 자체가 죽어 있다.**
(처음에는 멀티캐스트를 의심했지만 측정해 보니 멀티캐스트는 정상이었다. 아래가 실제 측정값이다)

| 측정 | 결과 |
|---|---|
| `ip route get 127.0.0.1` | `127.0.0.1 via 169.254.73.152 dev loopback0 table 127` ← 로컬호스트가 우회되고 있다 |
| UDP 127.0.0.1 → 127.0.0.1 | **실패 (timeout)** |
| TCP 127.0.0.1 → 127.0.0.1 | **실패 (timeout)** |
| UDP 멀티캐스트 239.255.0.1 (IF=127.0.0.1) | 성공 ← 멀티캐스트는 문제가 아니었다 |
| UDP/TCP → 10.255.255.254 (WSL 내부 주소) | 성공 |
| UDP/TCP → 192.168.219.102 (실제 IP) | 성공 |
| `C:\Users\<사용자>\.wslconfig` | `[wsl2] networkingMode=mirrored` |

WSL의 mirrored 모드는 Windows의 로컬호스트를 흉내내기 위해 `loopback0` 장치와 라우팅
테이블 `127`을 만들어 `127.0.0.0/8`을 Windows 쪽 경로로 넘긴다. 이 랩탑에서는 그 경로가
패킷을 버린다(방화벽·VPN 계열이 흔한 원인이다). 그래서 **ROS와 무관하게** 같은 PC 안의
프로세스 간 TCP·UDP가 전부 실패하고, DDS는 참가자를 발견해도 유니캐스트로 붙을 수 없어
`controller_manager`가 `robot_state_publisher`의 `/robot_description`을 못 받는다.
ros2cli 데몬의 `TimeoutError: [Errno 110]`도 같은 원인이다.

**우회 (sudo 불필요, 이미 자동 적용됨).** `scripts/lib_dds.sh`가 127.0.0.1 왕복을 먼저
시험해 보고, 죽어 있을 때만 `10.255.255.254`만 쓰는 Fast DDS 프로필을 만들어
`FASTRTPS_DEFAULT_PROFILES_FILE`로 넘긴다(유니캐스트 initial peers를 직접 나열하므로
멀티캐스트에도 의존하지 않는다). `04·05·06·07` 스크립트가 이것을 자동으로 호출한다.
직접 만든 터미널에서는 이렇게 한다:

```bash
source scripts/lib_dds.sh
so101_dds_setup
```

**우회로 해결되지 않는 것: ros2cli 데몬.** `ros2cli`는 데몬의 XML-RPC 주소를 `127.0.0.1`로
소스에 고정해 두었다(`/opt/ros/jazzy/lib/python3.12/site-packages/ros2cli/daemon/__init__.py:41`
→ `return '127.0.0.1', get_port()`). DDS는 우회할 수 있지만 이 채널은 우회할 수 없어서
`ros2 daemon status`와 `ros2 control ...`(데몬 경로를 탄다)은 계속 멈춘다.
`ros2 node list`도 탐색이 부분적으로만 채워질 수 있다. 그래서 이 프로젝트의 `04_smoke_test.sh`는
컨트롤러·하드웨어 인터페이스·액션·`/joint_states`·`/clock`을 **모두 rclpy 직접 호출**로 확인한다
(CLI 조회를 쓰지 않는다). 기능 자체는 전부 정상이다.

**근본 해결 (권장).** Windows에서 `C:\Users\<사용자>\.wslconfig`의 `networkingMode=mirrored`를
지우거나 주석 처리하고(= 기본 NAT 모드) PowerShell에서 `wsl --shutdown` 후 터미널을 다시 연다.
`./scripts/07_doctor.sh`의 4번 항목이 `[OK] 127.0.0.1 UDP 왕복 정상`이면 해결된 것이다.
mirrored 모드를 Windows↔WSL localhost 접속 때문에 일부러 쓰고 있다면 우회를 계속 써도 된다
(로봇 쪽 기능 차이는 없다).

수동으로 하려면 위에서부터 순서대로 시도한다.

```bash
# 1) 응답하지 않는 ros2cli 데몬 내리기 (조회 명령이 traceback 내는 원인)
ros2 daemon stop
ros2 node list --no-daemon        # 조회는 --no-daemon 으로

# 2) 모든 ROS 프로세스를 완전히 내리고 고아 공유메모리 정리
#    (강제 종료된 프로세스가 /dev/shm 에 세그먼트를 남기면 Fast DDS 가 막힌다)
pkill -f ros2_control_node; pkill -f robot_state_publisher; pkill -f move_group; pkill -f rviz2
ros2 daemon stop
rm -f /dev/shm/fastrtps_* /dev/shm/sem.fastrtps_*

# 3) 전송 방식을 바꿔 본다 (bringup 과 조회 터미널 모두 같은 설정이어야 한다)
source scripts/lib_dds.sh && so101_dds_setup   # 127.0.0.1 이 죽은 WSL 이면 이것부터
export FASTDDS_BUILTIN_TRANSPORTS=UDPv4        # 공유메모리 없이 UDP 로만
#   또는
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp   # 다른 DDS 구현

# 4) 그래도 안 되면 WSL 재시작 (시계 점프도 함께 해결된다)
#    Windows PowerShell 에서:  wsl --shutdown      → 다시 wsl -d Ubuntu
```

**시계 확인도 같이 한다.** WSL은 Windows 절전 후 시계가 어긋나고, 갑자기 동기화되며 몇십 분씩 점프한다.
그 순간 DDS의 타임아웃·liveliness가 깨져 위 증상이 나타난다.

```bash
date -u +%s     # Windows 시간과 크게 다르면 wsl --shutdown 후 재시작
```

검증 중 실제로 이 현상을 관측했다(46분 점프 직후 spawner 실패). 같은 launch가 재시작 후에는
컨트롤러 3개를 정상 활성화했으므로, 위 증상이 보이면 **설정을 의심하기 전에 이 부록을 먼저 실행한다.**
